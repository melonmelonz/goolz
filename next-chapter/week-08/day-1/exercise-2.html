Prioritize The Backlog

Exercise 2 / 5 . Level 1 . 30 min

Goal: take the messy audit and turn it into a plan with MoSCoW. I dumped everything from Exercise 1 into one list -- the two P1s, the P2s, the P3s, the four missing pieces -- and went item by item. The rule I held the whole time was the must-have test: if this isn't done, can someone still open ReEntry Tech and use it? If yes, it is not a Must. That one sentence did most of the sorting for me, and it disagreed with my gut more than once.

Must Have

Three to five, max. Every one earns its place by failing the "can someone still use it" test -- if it is not done, the app is broken or unusable or unshippable for my one user.

ItemWhy it's a MustEffort
P1 -- AI summary must not 500 in prodset OPENAI_API_KEY in Vercel and wrap the route so a key/API failure returns a graceful message, not a 500. Without it the headline AI feature crashes on the live URL.M
P1 -- guard the AI route's inputreject empty / non-URL input before the OpenAI call. Without it any fat-fingered paste takes the page down.S
Deploy to a working live URL"done" requires a real URL, and my user opens it from his phone. Localhost is not shippable.M
Empty state on the boardmy one user opens an app with zero rows; a blank rectangle reads as broken. For him the empty state is the first screen, so it is the app.S

Five Musts, totalling roughly M+S+M+S+M ≈ 2 + 0.75 + 2 + 0.75 + 2 = ~7.5 hours. That fits inside the ~12-14 hours of sprint time with real buffer, which is the point -- if my Musts had come out at 13 hours I would have had to cut one, because the first task always runs long.

The two Musts that argued with my gut

The empty state felt like polish -- my instinct filed it under Should. But the test asks about my user, and my user opens a board with nothing in it, so the empty state is literally his first impression of whether the app is alive. It stays. Going the other way: the stale-board-after-edit bug felt like a Must because editing is "core CRUD." But someone can absolutely use ReEntry Tech without editing -- they add, they read, they delete. So it drops to Should. The gate only asks for Create + Read end-to-end; edit is not load-bearing for "usable."

Should Have

Important, but the app still functions without them. These are the first things I pull up if I blow through the Musts -- not before.

  • P2 -- revalidate the board after an edit so the updated row shows without a manual refresh
  • P2 -- optimistic delete so the card disappears on click instead of lingering until refresh
  • P2 -- trim-and-presence validation on the create form (reject an all-spaces title)
  • Loading state / spinner while the AI summary is fetching
  • P3 -- mobile card overlap and ragged filter chips below 380px

Nice To Have

  • Second AI feature: "help me phrase a request to a parole officer / employer"
  • Save / favorite an opportunity
  • P3 -- real header tagline replacing the Week 4 placeholder (will sneak this into final cleanup)

Won't Do (This Sprint)

  • User accounts / auth / multi-user
  • Calendar view of appointments
  • Categories as their own CRUD UI
  • Reminders / notifications
  • Dark-mode polish beyond what the stylesheet already does for free
The one that hurt to cut

The "phrase a request" AI feature is genuinely the most me idea in the whole app, and it is a clean second AI-touch. It is also a feature someone can use the app without -- so it failed the test, and it went to Won't Do without a real argument. That is the discipline: the test does not care which feature I am proudest of. It only asks whether my user can get value without it. He can. Gone.

Deliverable

A prioritized backlog: five Musts under ~8 hours with S/M/L estimates, a Should list waiting in the wings, and an explicit Won't Do so the cut decisions are written down and cannot quietly creep back in at 11pm on Day 2. Next exercise spreads the Musts across the three half-days as dated, testable tasks.
