The Day-By-Day Sprint Plan

Exercise 3 / 5 . Level 2 . 30 min

Goal: take the five Musts and pin them to specific half-days, in the same vocabulary I used on the Friday agile board -- each task a tiny user story, an S/M/L estimate, and a Definition of Done that says exactly what proves it is finished. The four rules I am holding myself to: P1s go first, Musts get real time slots (not "work on stuff"), Day 3 morning is bugfix and polish only -- no new features on deploy day -- and I pad every estimate, because everything takes longer than I think.

Vocabulary Check -- so this reads like Friday

User story: "As a user, I can ___ so that ___." Estimate: S = under 30 min, M = 30-60 min, L = over an hour. Definition of Done: the observable thing that proves it works -- not "I wrote the code" but "I clicked it and saw X."

Day 1 -- today, afternoon block (~2 hours)

Block 1 (~1h) -- P1: AI summary survives production.

  • Story: As a user, I can paste a job link on the live site and get a summary instead of a crash.
  • Tasks: set OPENAI_API_KEY in Vercel env; wrap the route in try/catch so a key/API failure returns a friendly "couldn't summarize that one" message; redeploy a preview. (M)
  • Done: on the preview URL, a valid posting link returns a summary (200), and a forced failure returns the friendly message -- no 500, page stays up.

Block 2 (~1h) -- P1: guard the AI input + P2: stale board after edit.

  • Story: As a user, an empty or junk paste tells me to fix it instead of breaking the page; and when I edit an opportunity I see the change immediately.
  • Tasks: reject empty / non-URL input before the OpenAI call (S); add revalidation after the PUT so the board reflects the edit without a hard refresh (S). (S + S)
  • Done: empty box and "not a url" both show an inline message and never fire the call; editing a title updates the card on the board with no manual refresh.

Day 2 -- full build day (~6 hours)

Morning lab (~2.5h)

  • Deploy to production on a real URL (M). Story: As a user, I can open ReEntry Tech at a public HTTPS URL on my phone. Done: the live URL loads the board, create works end-to-end, AI summary works -- tested from a phone, not just the laptop.
  • Empty state on the board (S). Story: As a first-time user with no opportunities yet, I see a friendly prompt and a clear "Add your first one" button, not a blank rectangle. Done: a board with zero rows (or a filter matching zero) renders the empty state with a working CTA.

Afternoon lab (~2.5h)

  • Should-have: presence validation + optimistic delete (S + S). Done: an all-spaces title is rejected with a message; a deleted card disappears on click.
  • Start documented user activity (M, continues Day 3). Story: a real person uses the live app. Done: at least one non-me user has added an opportunity on the live URL; I have a screenshot and a sentence of their feedback.

End of afternoon (~30 min) -- test everything. Click through every feature on the live URL, write down every new bug. This is where Day 3's first block comes from.

Day 3 -- morning only (~3 hours), deploy in the afternoon

  • First block (~1h): fix the bugs found in Day 2 testing. No new features -- triage what the click-through surfaced.
  • Second block (~1h): one quick Should-have -- AI loading spinner, plus the mobile card-overlap fix if there is room.
  • Pre-lunch (~30 min): final cleanup -- strip the console.logs from the AI route, swap the Week 4 placeholder tagline for the real pitch, check the layout at 360px.
  • Afternoon: finish documented user activity (get to 2-3 users + screenshots), then the final deploy.
Why Day 3 morning has no new features

Shipping a new feature on deploy day is the classic way an app that worked at lunch is broken at 4pm. Day 3 morning is reserved for fixing what Day 2's testing surfaced and one small polish item -- nothing that can introduce a new failure path right before the thing goes live. If I finish the Musts early, I pull from Should; I do not borrow trouble by scheduling Shoulds into the main plan.

Deliverable

A day-by-day plan with specific, checkbox-able tasks, each a user story with an S/M/L estimate and a Definition of Done. P1s sit in Day 1 Block 1. Day 3 is bugfix and deploy. The Musts add up to roughly eight hours against twelve-plus available, which is the buffer the rules demand. Next exercise hands it to a partner to find the holes I cannot see.
