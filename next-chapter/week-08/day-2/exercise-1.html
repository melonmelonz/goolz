Deploy to Production (Vercel)

Exercise 1 / 5 . Level 2 . 40 min

Goal: a real URL that my user can open on his phone, cold, with the board reading, create working, and the AI summary returning bullets -- all against the production database, not my laptop. This is Must-Have number three and it anchors the whole day, so it goes first. The two P1s I cleared yesterday were about the AI route surviving; this one is about the app existing somewhere other than localhost. I had been treating "I have a Vercel project" as if it meant "I am deployed," and the gap between those two is exactly what this exercise closes.

The environment is the whole battle

Everything that bites me on deploy lives in the environment. On my laptop the secrets sit in .env.local, which Git ignores and Vercel has never seen. In production those same two variables -- the OpenAI key and the database connection string -- have to be set explicitly in the dashboard, on the Production environment specifically. Production, Preview, and Development are three separate buckets; setting a key on Preview and assuming Production inherits it is how the AI summary 500'd in the first place. 

# Vercel dashboard -> Settings -> Environment Variables
# set BOTH of these, and make sure Production is checked (not just Preview)
OPENAI_API_KEY = sk-...
DATABASE_URL   = postgres://user:pass@prod-host:5432/reentry?sslmode=require

# a key set on Preview but not Production = a green build that 500s on the
# first real click. ask me how I know.
A build that compiles is not an app that works

Vercel printed "Build Completed" in green and I almost called it done. But the build only proves my code compiles -- it runs no real requests, touches no real database. The first time I opened the live URL the board threw, because the production database had never had a migration run against it. The green checkmark was telling the truth about my syntax and nothing about my app. Build success is necessary, not sufficient, and I now read that cheerful green with suspicion on purpose.

The database deploy is a separate act

The code push does not change the database. My schema lives in Prisma and the production database only learns about it when I run the migration against the prod connection string. This is the trap my partner caught in the mini-demo: push code with a schema change, skip the migrate, and the build goes green while the first query against the missing column throws at runtime. So before I trust the live URL, I run the migration explicitly against prod. 

# run the committed migrations against the PRODUCTION database
# (deploy, not dev -- this does not generate new migrations, it applies them)
DATABASE_URL="postgres://...@prod-host/reentry" npx prisma migrate deploy

# sanity check that the prod schema now has the Opportunity + Category tables
npx prisma migrate status

This is the part I have been mentally skipping, because on localhost prisma migrate dev does both steps at once and I forgot they were ever two things. In production they are firmly two things: deploy the code, then deploy the schema. Either one alone is a broken app that looks deployed.

Smoke-test the live URL like it is the real thing -- because it is

Once the build is green and the migration has run, I open the production URL on my phone, on cellular, not on my laptop on my own wifi. I want it as close to my user's actual conditions as I can get. Three things have to work, in order: the board reads, a create sticks, the AI summary returns. If any of them throws, deploy is not done and nothing else on today's list starts.

Done means a stranger can use it, not that it compiled

The whole reason this is a Must-Have and not a checkbox is the definition of done from Day 1: it works, it is deployed, a real person can use it. My user cannot open localhost from a county-issued phone on cellular. Until the production URL reads, creates, and summarizes for someone who is not me, deploy is unfinished -- no matter how green the build log is. The forklift cert deadline he is racing is real, and the URL has to be real too.

Deliverable

A live production URL that passes all four smoke tests from a phone on cellular: board reads, create sticks, AI summary returns bullets, bad input degrades to a sentence instead of a crash. Both env vars set on Production, the migration applied against the prod database, the build green and -- this is the part I no longer take for granted -- the app actually working on the first real click. Must-Have three, crossed off by clicking it, not by reading it. Commit, then on to the empty state.
