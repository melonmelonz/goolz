AI Summary Loading State

Exercise 4 / 5 . Level 1 . 25 min

Goal: while the AI summary is thinking, the UI should say so. The OpenAI call takes two to four seconds, and right now the screen just freezes -- the button stays clickable, nothing moves, and people assume it did not register and click again, firing a second call. The fix is tiny: track a loading flag, disable the button while the call is in flight, and show a spinner with a word. This is the smallest thing on the whole board and it changes the perceived quality more than anything else I will touch today.

The problem is silence, not slowness

Two to four seconds is not actually that long. The problem is that the app says nothing during it, and silence reads as broken. A user pastes a link, taps Summarize, and the screen sits there looking exactly like it did before the tap -- so a reasonable person concludes the tap missed and taps again. Now I have two OpenAI calls running, two charges, and a race over which response renders. The fix is not to make the call faster; it is to make the wait legible.

The loading-state code

// app/Summarize.jsx -- a flag, a disabled button, a spinner
import { useState } from "react";

function Summarize() {
  const [loading, setLoading] = useState(false);
  const [summary, setSummary] = useState(null);

  async function onSummarize(url) {
    setLoading(true);              // button disables, spinner shows
    try {
      const res = await fetch("/api/summarize", {
        method: "POST",
        body: JSON.stringify({ url }),
      });
      const data = await res.json();
      setSummary(data.summary ?? data.error);
    } finally {
      setLoading(false);           // always re-enable, even if it threw
    }
  }

  return (
    <button onClick={() => onSummarize(url)} disabled={loading}>
      {loading ? "Reading the posting..." : "Summarize"}
    </button>
  );
}

The disabled={loading} is the whole double-click fix -- a disabled button cannot be clicked, so the second call can never fire. The finally is the part I would have forgotten a few weeks ago: the button has to re-enable whether the call succeeds or throws, or one failed summary leaves the button dead forever. And the label change from "Summarize" to "Reading the posting..." does double duty as the spinner's words, because a verb is more reassuring than a bare spinning circle.

The cheapest fix with the biggest perceived-quality payoff

This took twenty minutes and it is the single largest jump in how finished the app feels. That is the lesson worth keeping: perceived quality and engineering effort are not the same axis. The AI route itself -- the part that survives production, guards bad input, degrades instead of crashing -- was hours of careful work. The loading state is a boolean and a disabled attribute, and to the person using it, it is the difference between "this app is thinking for me" and "this app is frozen." When time is short, the highest-leverage fixes are often the ones that change what the user feels, not what the code does.

Verified by clicking it on the live URL: pasted a real posting, tapped Summarize, watched the button gray out and the label switch to "Reading the posting..." for about three seconds, then the bullets came back and the button re-enabled. Tried to double-tap during the wait and could not -- the button was dead, exactly as intended. Then forced an error and confirmed the button came back to life afterward instead of staying stuck.

Deliverable

A loading state on the AI summary: a flag that disables the button and swaps in a working-verb label while the call runs, with a finally that always re-enables. No more double-clicks, no more frozen-looking screen, no more silent two-to-four-second void. The smallest commit of the day and one of the most noticeable. One Should-have left on my list after this, and the afternoon still has room. Commit.
