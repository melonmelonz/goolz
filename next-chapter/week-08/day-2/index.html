Yesterday was paperwork. Today is the build. The whole arc of Day 1 -- the kickoff, the honest audit, the MoSCoW sort, the day-by-day plan -- existed so that this morning I could sit down already knowing exactly what to touch and, more importantly, what to leave alone. The discipline today is a single sentence taped to the monitor: if it is not on the Must-Have list, it does not exist this week. I will feel the pull all day -- a nicer card layout here, a second AI feature there, the parole-officer-letter idea I genuinely love and already moved to Won't Do. The whole game today is to keep my hands on the four things that matter and off the dozen that would feel productive. Six hours. A list that ends the day shorter than it started. That is the win.

Lecture Notes -- Deploying to Vercel

The single biggest deploy trap is the environment. On my laptop, secrets live in .env.local, which Git ignores and Vercel never sees. In production those same variables have to be set in the Vercel dashboard, per environment -- Production, Preview, Development are three separate buckets, and a key set on Preview is not magically present on Production. This is exactly how the AI summary 500'd in the first place.

ConceptWhat it means
build time vs runtimethe build compiles your code; runtime is when a real request runs it -- a green build can still crash on the first click if a runtime env var or the prod DB is wrong
preview vs productionevery push gets a throwaway preview URL; production is the one real URL my user opens -- env vars must be set on Production, not just Preview
migrationscode deploy does not change the database -- the prod schema only updates when prisma migrate deploy runs against the prod connection string
# env vars live in the Vercel dashboard, per environment, NOT in the repo
# Settings -> Environment Variables (check Production)
OPENAI_API_KEY = sk-...
DATABASE_URL   = postgres://...@prod-host/reentry

# the schema is not deployed by the code push -- run it against prod:
npx prisma migrate deploy

The mental model I keep messing up: deploying the code and deploying the database are two different actions. The build can be perfectly green and the app still throws on its first real query because the prod database never got the migration. Build success is necessary, not sufficient.

Lecture Notes -- What An Empty State Is For

An empty state is the screen a feature shows when it has nothing to show yet -- zero rows, no results, a fresh account. It is easy to dismiss as polish, and for most apps with a seeded demo database it sort of is. For mine it is not, because my one user is, by definition, opening an app with nothing in it. The very first thing he ever sees is the empty state. A blank grey rectangle is indistinguishable from a broken page; a friendly line plus an obvious "Add your first one" button is the difference between "this works, I get it" and "is this thing on?"

There are two empty states, not one, and they need different copy. The zero-data state is the brand-new board -- nothing has ever been added, so the message is a welcome and a call to action. The filtered-to-zero state is when there is data but the current filter matches none of it -- "no jobs yet" is true and reassuring, whereas the welcome copy would be a lie. Same empty grid, two very different sentences.

Lecture Notes -- Should-Have Sweep, Only After The Musts

Should-haves are real improvements the app survives without. They are allowed this afternoon only because the Musts are done -- not before. The trap is the satisfying Should that feels like progress while a Must sits unfinished; the order protects me from myself. Three small wins are queued: trim-and-presence validation so an all-spaces title cannot insert a blank card, an optimistic delete so the card vanishes on click instead of lingering until a refresh, and a loading state on the AI button so the 2-4 second OpenAI call does not look frozen. Small, each one. None of them is a feature -- they are the difference between the app feeling broken and the app feeling finished.

// optimistic delete -- the card leaves on click, reconciles on the server
import { useOptimistic } from "react";

const [shown, removeOptimistic] = useOptimistic(
  opportunities,
  (state, removedId) => state.filter((o) => o.id !== removedId)
);

async function onDelete(id) {
  removeOptimistic(id);              // card vanishes immediately
  await deleteOpportunity(id);       // server catches up; revalidate reconciles
}
Lecture Notes -- Test Like A Stranger

The last thing I do today is the opposite of building. I open the live URL, not localhost, and I go through every feature trying to break it -- paste a garbage link, submit an empty form, delete a card and slam the back button, view it on a narrow phone. Building makes me confident, and confidence hides bugs; testing like a hostile stranger surfaces them. Every new bug goes straight into the backlog with a P1/P2/P3 next to it. I do not fix them tonight. That list is exactly what Day 3 morning is for -- I want to walk into tomorrow knowing what is broken, not discover it during the gate demo on Day 4.

  • Exercise 2 Empty State On The Board build the zero-rows screen -- a friendly line plus an "Add your first one" CTA -- and handle filtered-to-zero with its own copy ("no jobs yet" vs "nothing here yet"), so a fresh app never reads as a broken one
  • Exercise 3 Should-Have Sweep: Validation + Optimistic Delete trim-and-presence validation so an all-spaces title is rejected, and optimistic delete so the card vanishes on click and reconciles on the server -- two small wins, only now that the Musts are crossed off
  • Exercise 4 AI Summary Loading State a spinner and a disabled button while the 2-4s OpenAI call runs, so nobody double-clicks a frozen-looking screen -- the cheapest fix on the board with the biggest jump in perceived quality

Verbal Mini-Demo -- The Live URL On A Phone

Two minutes to my partner, and this time it was not a slide -- I pulled out my phone, opened the production URL cold, and walked the loop in front of him: the board reads, I add a forklift-cert opportunity, it shows up newest-first, I paste a real job posting and watch the AI summary come back as bullets. No localhost, no "imagine this works." The point I was making out loud is that the demo is no longer a description of something on my laptop; it is a thing on the internet that a person who is not me can open. That is the Must-Have I cared most about, and saying it while it actually worked on a 5-inch screen felt different than promising it would.

His challenge question landed where I was soft: "what happens on the production database if you push code with a schema change but forget the migrate?" I had to be honest -- the build goes green, the deploy succeeds, and the first query against the missing column throws at runtime, in front of whoever opened the page. The code deploy and the database deploy are two separate acts, and Vercel cheerfully lets you do one without the other. That is the exact trap I am most likely to fall into tomorrow when I am tired and pushing fast, so naming it out loud was less a demo answer and more a note to my future self.

The Thing That Clicked Today

The thing that clicked is that a build compiling is not the same as an app working, and I had been quietly conflating the two for weeks. Vercel says "Build Completed" in cheerful green and some part of my brain reads that as "done." But the build only proves my code is syntactically willing to run -- it says nothing about whether the prod database has the right columns, whether the env var is set on Production and not just Preview, whether the first real click returns data or a 500. The deploy today was green on the first try and broken on the first click, because the migration had not run against prod. The green checkmark was lying to me, and learning to distrust it on purpose is the whole lesson.

The other thing, quieter, is how good it feels to work a list I already decided on. All the agony of Day 1 -- what is a Must, what is a Should, what do I cut -- bought me a morning where I did not have to decide anything, only execute. There is a real pull all day toward the new shiny idea, and the only thing that held was that I had written the list yesterday, when I was calm, and today I just trusted yesterday-me. By lunch the production URL worked on my user's phone -- the actual guy, the forklift cert, the folded-up piece of paper -- and the empty state meant the first thing he saw was a welcome and not a blank rectangle. Crossing those two off felt like the opposite of the growing untouched list that haunted Week 5. Shorter, not longer. That is the day.
