Style the Cards

Exercise 4 / 5 . Level 2 . 30 min

Goal: turn the raw list into something that reads like a product. Cards, a grid that reflows, a colored badge per opportunity type. The data has not changed at all since Exercise 2 -- this is purely presentation -- and that separation is exactly the thing I want to keep clean. The query lives in one place; how a row looks lives in another.

A reusable card component

// app/opportunities/opportunity-card.js
import Link from "next/link";

const TYPE_COLORS = {
  job: "#5E957A",
  certification: "#3498db",
  service: "#9b59b6",
};

export default function OpportunityCard({ opportunity }) {
  const badge = TYPE_COLORS[opportunity.type] || "#8A8E87";

  return (
    <Link href={`/opportunities/${opportunity.id}`} className="card-link">
      <article className="opp-card">
        <div className="opp-card-head">
          <h2>{opportunity.title}</h2>
          <span className="badge" style={{ background: badge }}>
            {opportunity.type}
          </span>
        </div>
        <p>{opportunity.description}</p>
        {opportunity.org && (
          <div className="opp-card-foot">Posted by {opportunity.org.name}</div>
        )}
      </article>
    </Link>
  );
}

A component that takes one opportunity prop and returns its visual. It does not know about the query, the array, or where the data came from -- hand it a row, it renders a card. That is the boundary I care about: the card is dumb about data, the page is dumb about layout, and neither has to change when the other does. The whole card is wrapped in a Link to /opportunities/[id], which is the navigation hook Exercise 5 lands on.

The type-to-color map is a lookup, not a chain of ternaries

I could have written opp.type === "job" ? green : opp.type === "certification" ? blue : ... and it would work. The object map TYPE_COLORS[opportunity.type] reads better, adds a new type with one line instead of a new branch, and -- the part I actually like -- the || "#8A8E87" fallback means an unexpected type renders gray instead of crashing or rendering nothing. ReEntry Tech's types are a small fixed set today, but the day someone seeds a "housing" type I have not styled, it shows up gray and legible instead of breaking the grid. Defensive in the cheap, correct way.

The grid

// app/opportunities/page.js
import { prisma } from "@/lib/prisma";
import OpportunityCard from "./opportunity-card";

export default async function OpportunitiesPage() {
  const opportunities = await prisma.opportunity.findMany({
    orderBy: { createdAt: "desc" },
    include: { org: true },
  });

  return (
    <div>
      <h1>Opportunities</h1>
      <p>{opportunities.length} listings</p>
      <div className="opp-grid">
        {opportunities.map((o) => (
          <OpportunityCard key={o.id} opportunity={o} />
        ))}
      </div>
    </div>
  );
}

/* in the stylesheet */
.opp-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(300px, 1fr));
  gap: 16px;
}

Note I dropped back to a server component here. Exercise 3's client list was for live search; this exercise is about presentation, so I render the styled grid the simple server-side way and would layer the search component back on top when I want both. The grid is one line of CSS doing real work: auto-fill with minmax(300px, 1fr) fits as many 300px-minimum columns as the viewport allows and stretches them to fill -- three across on a laptop, one on a phone, no media query. I keep relearning that the modern layout primitives make most of my old breakpoint code unnecessary.

Honest note: inline styles work but a real app moves them to CSS

The lecture leans on inline style={{}} objects, which are fine for getting pixels on screen fast and I am not going to pretend otherwise mid-lab. But the genuine :hover lift on a card -- shadow grows, card rises a few pixels -- cannot be expressed inline, because there is no inline pseudo-class. So the hover lives in the stylesheet (.opp-card { transition: ... } .opp-card:hover { transform: translateY(-2px); }) and the structural styles can stay inline or move there too. The split I am drawing: dynamic per-row values like the badge color stay in JS where the data is; everything static and stateful-on-the-element lives in CSS where it belongs. Mixing those is how a codebase ends up with the same shadow defined four ways.

Checkpoint

It looks like an app now -- a reflowing grid of cards, color-coded by type, each one a link. And the data layer never moved: the query is identical to Exercise 2. Presentation got richer without the database knowing or caring. Last piece is the click target those cards already point at.
