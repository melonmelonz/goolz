Day 3 -- API Routes: READ

NCD . WK6 . D3 . five exercises loaded . the database reaches the screen

The database has rows in it now. Yesterday I defined Organization, Opportunity, and Tag, pushed them to Neon, and seeded a handful of real-ish listings. But none of it is visible. The whole thing lives in a Postgres instance in some region I picked off a dropdown, and the actual ReEntry Tech app -- the pages someone leaving SCI Somerset would open -- still renders nothing. Today closes that gap. Schema to screen, the full-stack loop, the thing every app I use does a hundred times a second.

Here is the honest reframe, because the lecture frames today as new and for me it mostly is not. I have written GET handlers before. Every Pages Function I shipped this program -- the visitor counter, the notepad's functions/api/docs.js -- was a request coming in, a read happening, JSON going back out. So "an API route returns data as JSON" is not the lesson. The two genuinely new things are: Next.js's file convention for routes (a route.js exporting a function named GET, same folder-is-the-router idea as the pages), and the part that actually surprised me -- a server component can skip the HTTP hop entirely and query Prisma inline. No fetch. No endpoint. The page is the data fetch.

That second one is worth sitting with. My instinct from two years of frontends is page-makes-a-request, request-hits-an-endpoint, endpoint-talks-to-the-database. Three hops, and the first one goes over the network. A Next.js server component collapses the first two: the component runs on the server, so it can await prisma.opportunity.findMany() directly and ship finished HTML. The API route still exists and still matters -- I need it the moment a client component wants data for search -- but it is no longer the only door to the database. Today I build both doors and write down exactly when I would reach for each.

Lecture Notes -- The Full-Stack Loop

The whole arc, one line per stage, my project plugged in:

1. Schemaprisma/schema.prismadefines the Opportunity model
2. Seedprisma/seed.jsfills the table with sample rows (done yesterday)

Each stage is upstream of the next. The interesting wrinkle Next.js adds is that stage 4 can reach all the way back to stage 1 without stopping at stage 3 -- a server component page queries Prisma itself. Stage 3 is for when something on the client needs the data later.

Lecture Notes -- A GET Route Handler

The convention: a file at app/api/<thing>/route.js becomes the endpoint /api/<thing>, and you export a function named after the HTTP method.

// app/api/opportunities/route.js
import { prisma } from "@/lib/prisma";
import { NextResponse } from "next/server";

export async function GET() {
  const opportunities = await prisma.opportunity.findMany({
    orderBy: { createdAt: "desc" },
  });
  return NextResponse.json(opportunities);
}

Three lines of logic: query, wrap as JSON, return. NextResponse.json() sets the Content-Type and status for me -- the same headers I used to set by hand in a Pages Function. The @/lib/prisma import is the singleton from yesterday, not a fresh new PrismaClient(). That distinction is load-bearing and I have an exercise on why.

Lecture Notes -- Server Component vs. Client Fetch

Two ways to get the same list onto the page. The choice is not stylistic -- it follows from whether the data reacts to the user.

// Option 1 -- server component (default). No fetch.
export default async function OpportunitiesPage() {
  const opps = await prisma.opportunity.findMany();
  return ( /* render opps */ );
}

// Option 2 -- client component. Fetches the route.
"use client";
const [opps, setOpps] = useState([]);
useEffect(() => {
  fetch("/api/opportunities")
    .then(r => r.json())
    .then(setOpps);
}, []);

Option 1 is simpler and faster: it runs on the server, queries the database, and ships finished HTML -- no loading spinner, the data is already there when the page arrives. Option 2 costs a round-trip and a loading state, and you reach for it only when you need interactivity the server cannot pre-bake: search, filters, live updates. My rule for the week -- static read, server component; reacts to the user, client component.

Verbal Mini-Demo -- What Is an API Route

Partner asked me to open my route.js and explain it like they had never seen Next.js. So: the file lives at app/api/opportunities/route.js, and that path on disk is the URL -- a request to /api/opportunities lands here, same folder-is-the-router idea as the pages. I export async function GET() because this handles the GET method; if I exported a POST too it would handle submissions, but that is tomorrow. Inside, prisma.opportunity.findMany() runs a SELECT against Postgres and hands back an array of plain objects. NextResponse.json(opps) serializes that array and sets the headers. That is the entire endpoint.

Their follow-up was the good one: "If the URL were wrong, where would the error show up?" Depends which URL. If my fetch string is wrong -- I typed /api/opportunites, missing a u -- Next.js has no route file there, returns a 404, and my r.json() chokes on an HTML error page instead of JSON. That surfaces in the browser console on the client. If the database URL is wrong, the route file is fine but findMany throws, and the error shows up server-side in my terminal, not the browser -- which is exactly why I want a try/catch returning a clean 500, so the client gets "failed to fetch opportunities" instead of a hang.

Then I showed them the part I actually find interesting: my board page does not call this route at all. It is a server component, so it queries Prisma directly and the route only exists for tomorrow's client-side search. Their reaction was mine yesterday -- "wait, so when do you even need the route?" And that is the whole lesson, so I let them sit in it.

The Thing That Clicked Today

For years "the API" was a place. A separate server, its own repo half the time, a thing the frontend talked to over the wire and the two sides agreed on a contract and argued about it in standup. The mental model had a hard border down the middle, and a lot of my job was passing data across it cleanly. Today that border got blurry in a way I am still turning over. A server component is frontend -- it returns JSX, it renders a page -- and it also reaches straight into Postgres with no endpoint in between. The thing I was trained to treat as two machines is one function.

It is the same move as the last three days, one layer up again. Folder-is-the-router. File-is-the-endpoint. Schema-is-the-table. And now: the page can be the query. Each one erases a seam I used to maintain by hand and a contract I used to keep in sync. I keep waiting to find where the abstraction leaks -- and it does, the instant I need useState and the page snaps back to needing a real fetch and a real route. But that is the honest version of the lesson, not a disappointment in it. The seam is still there. Next.js just lets me not pay for it until the page actually earns the cost.
