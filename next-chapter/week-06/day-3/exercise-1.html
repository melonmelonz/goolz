Build the GET Route

Exercise 1 / 5 . Level 1 . 25 min

Goal: a working endpoint at /api/opportunities that returns every row in the table as JSON, provable by opening a URL. This is the part I have done before in a different costume -- a Pages Function is the same shape -- so my real job here is to learn the Next.js convention exactly and not paper over the one detail that is genuinely new to me: the import.

The file is the route

No config, no router registration. I make a folder and a file and the path becomes the URL: 

app/
  api/
    opportunities/
      route.js     -->  /api/opportunities

Same instinct as the pages yesterday. The directory structure is the routing table. route.js is the reserved filename for an endpoint, the way page.js is reserved for a rendered page.

The handler

// app/api/opportunities/route.js
import { prisma } from "@/lib/prisma";
import { NextResponse } from "next/server";

export async function GET() {
  try {
    const opportunities = await prisma.opportunity.findMany({
      orderBy: { createdAt: "desc" },
    });
    return NextResponse.json(opportunities);
  } catch (error) {
    return NextResponse.json(
      { error: "Failed to fetch opportunities" },
      { status: 500 }
    );
  }
}

findMany with no where is "give me all rows," and orderBy: { createdAt: "desc" } puts the newest listing on top, which is what a board wants. The try/catch is not ceremony. If Neon is asleep or the connection string rots, I want the client to receive a clean 500 with a message, not a thrown exception that leaks a stack trace or hangs the request. I learned that lesson the boring way on Workers.

The detail I actually came here for: import the singleton, never new PrismaClient()

I import { prisma } from @/lib/prisma -- the global singleton I set up yesterday -- and I do not write const prisma = new PrismaClient() at the top of the route. In dev, Next.js hot-reloads this module on every save, and a fresh client per reload opens a fresh pool of database connections that never get closed. After a dozen saves Neon starts refusing connections and the error looks like a database problem when it is actually a me problem. The singleton stashes one client on globalThis and reuses it across reloads. This is the single most common Prisma-in-Next.js footgun and the reason I built lib/prisma.js a day before I needed it.

Test it in the browser

Dev server running (npm run dev), then open the URL directly. A GET request is just visiting a URL, so the browser is the whole test rig: 

http://localhost:3000/api/opportunities

Out comes my seed data as raw JSON -- an array of objects, each with id, title, type, createdAt, orgId. Seeing the actual createdAt timestamps in descending order told me the orderBy took effect, not just that the query ran.

Footgun: createdAt comes back as a string, not a Date

In my server code createdAt is a JS Date object. The moment it goes through NextResponse.json() it gets serialized to an ISO string like "2026-06-01T14:22:09.001Z", because JSON has no date type. So anything consuming this endpoint receives a string and has to new Date(...) it back before calling .toLocaleDateString(). Not a bug, just the nature of crossing the wire -- but it is the kind of thing that bites you at render time with "createdAt.getFullYear is not a function," and I would rather know now than debug it in a card component later.

Checkpoint

The endpoint exists, returns the table as JSON, sorts newest-first, and fails safely. It is reachable by anything that can make an HTTP request. The interesting twist comes next -- the page I build in Exercise 2 will not actually call it.
