Add Search (Client Component)

Exercise 3 / 5 . Level 2 . 30 min

Goal: a search box that filters the board as I type. This is the exercise where yesterday's simple server component stops being enough, and I want to be precise about why, because the reason is the whole shape of Next.js. Search needs state -- the current query string, held across keystrokes. State means useState. useState only runs in a client component. And a client component cannot await prisma.findMany(), because it runs in the browser, where there is no database and no business having one. So the instant I want live search, the data has to come back through the API route I built in Exercise 1.

Pull the list into a client component

I split the search UI out into its own file so only the interactive part pays the client-side cost: 

// app/opportunities/opportunity-list.js
"use client";

import { useState, useEffect } from "react";

export default function OpportunityList() {
  const [opportunities, setOpportunities] = useState([]);
  const [search, setSearch] = useState("");
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch("/api/opportunities")
      .then((r) => r.json())
      .then((data) => {
        setOpportunities(data);
        setLoading(false);
      });
  }, []);

  const q = search.toLowerCase();
  const filtered = opportunities.filter(
    (o) =>
      o.title.toLowerCase().includes(q) ||
      (o.type && o.type.toLowerCase().includes(q))
  );

  if (loading) return <p>Loading opportunities...</p>;

  return (
    <div>
      <input
        type="text"
        placeholder="Search by title or type..."
        value={search}
        onChange={(e) => setSearch(e.target.value)}
      />
      <p>Showing {filtered.length} of {opportunities.length}</p>
      {filtered.map((o) => (
        <div key={o.id} className="opp">
          <h2>{o.title}</h2>
          <span>{o.type}</span>
        </div>
      ))}
    </div>
  );
}

Notice what came back that I deleted yesterday: loading state, a spinner branch, a useEffect to fetch. All the machinery the server component let me skip is back, and it is back for a concrete reason -- a client component renders before its data arrives, so it has to represent the gap. The filtered array is derived on every render from opportunities and search; I do not store it in state, because it is a function of two things that already are state. Storing it would be a third source of truth to keep in sync, which is a bug waiting to happen.

The decision: filter in memory, not on the server

I fetch all opportunities once and filter the array client-side as the user types. The alternative is to hit the server on every keystroke with /api/opportunities?q=... and let Postgres do the filtering. For ReEntry Tech right now -- a few dozen listings -- in-memory is obviously correct: one fetch, instant filtering, zero network per keystroke, and it works offline once loaded. Server-side filtering earns its keep when the table is too big to ship to the browser, or when the filter needs the database (full-text search, joins, ranking). Same tradeoff I would make caching anything: pull the whole set when it is small enough to hold, query per-request when it is not. I am holding it.

The page shrinks to a shell

// app/opportunities/page.js
import OpportunityList from "./opportunity-list";

export default function OpportunitiesPage() {
  return (
    <div>
      <h1>Opportunities</h1>
      <OpportunityList />
    </div>
  );
}

The page itself can stay a server component -- a plain heading and a child -- while only OpportunityList carries the "use client" boundary. That is the pattern the docs keep pushing: push the client directive as far down the tree as it will go, so the interactive island is small and everything above it still renders on the server.

Bonus I tried: server-side filtering by query param

For the contrast, I taught the route to read a query param so a category filter can live in the URL:

export async function GET(request) {
  const { searchParams } = new URL(request.url);
  const type = searchParams.get("type");
  const opportunities = await prisma.opportunity.findMany({
    where: type ? { type } : {},
    orderBy: { createdAt: "desc" },
  });
  return NextResponse.json(opportunities);
}

Now /api/opportunities?type=certification filters server-side, and the filter is shareable -- it lives in the URL, so I can link straight to "all certifications." That is the real win of server-side filtering for me: not performance at this scale, but that the filtered view has an address. The text-search box stays client-side; a URL-shaped category filter would go server-side. Different jobs, different doors.

Checkpoint

Live search works, and I can articulate the exact line I crossed to get it: state forced the client boundary, the client boundary forced the fetch, the fetch needed the route. The server component was simpler and I gave it up deliberately for one feature, not by habit. Next, make the thing look like an app.
