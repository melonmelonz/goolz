Render the Board (Server Component)

Exercise 2 / 5 . Level 1 . 30 min

Goal: the data on the screen. The opportunities board, rendered from the database, as a list someone could actually read. And I am building it the simple way -- a server component that queries Prisma inline, no fetch, no endpoint, no loading state. This is the option that surprised me, so I want to feel it work before I reach for the heavier client-side version tomorrow.

The page

// app/opportunities/page.js
import { prisma } from "@/lib/prisma";

export default async function OpportunitiesPage() {
  const opportunities = await prisma.opportunity.findMany({
    orderBy: { createdAt: "desc" },
    include: { org: true },
  });

  return (
    <div>
      <h1>Opportunities</h1>
      <p>{opportunities.length} listings</p>

      {opportunities.length === 0 ? (
        <p>No opportunities yet. Check the seed.</p>
      ) : (
        opportunities.map((opp) => (
          <div key={opp.id} className="opp">
            <h2>{opp.title}</h2>
            <p>{opp.description}</p>
            <div className="meta">
              <span>{opp.type}</span>
              {opp.org && <span>Posted by {opp.org.name}</span>}
            </div>
          </div>
        ))
      )}
    </div>
  );
}

The function is async and I await the query right inside it. That only works because this is a server component -- it runs on the server, where talking to the database is allowed and ordinary. The page is not asking an API for data; it is the thing that gets the data. By the time any HTML reaches the browser, the rows are already baked into it.

include: { org: true } is the join I'd write by hand in SQL

Without include, each opportunity comes back with an orgId (the foreign key, an integer) but no org object -- so opp.org.name would be undefined. Adding include: { org: true } tells Prisma to follow the relation and attach the full Organization row. In raw SQL this is a JOIN organizations ON organizations.id = opportunities.org_id; Prisma generates that join from the one word org. The cost is real -- it is more data per row and an extra join -- so you include relations you render and skip the ones you do not. I render the org name, so I include org.

The empty-state branch

The ternary on opportunities.length === 0 is not decoration. The first time I loaded this page before seeding finished, I got a blank white nothing and spent a minute wondering if the query was broken when the table was just empty. A real app gets emptied all the time -- a fresh deploy, a filtered view with no matches, an org that deleted all its postings. "No opportunities yet" is the difference between "the page works and there is nothing to show" and "the page is broken," and the user cannot tell those apart unless I tell them.

No "use client", no useEffect, no loading spinner -- and that is the point

Compare this to every React data-fetch I have written before: a useState for the list, a useState for loading, a useEffect that fetches, a if (loading) return <Spinner/>. All of that exists to handle the gap between "page rendered" and "data arrived." A server component has no gap -- the data is fetched before the render, on the server -- so all of that machinery just evaporates. Fewer states means fewer states to get wrong. I am keeping this page server-side as long as it has no reason to react to the user, which holds right up until I add search in Exercise 3.

Test it

http://localhost:3000/opportunities. The seed listings render as a plain list, the count is right, each one shows its org name -- which confirms the relation resolved, not just the base query. View-source on the page shows the titles already in the HTML, not injected by JS afterward. That is the server component doing its job: the data shipped with the document.

Checkpoint

The full-stack loop is closed for the read path. Schema, seed, and now a page that renders the rows -- with the relation joined and an honest empty state. It is unstyled and static. Exercise 3 makes it react to typing, and that is where the architecture has to bend.
