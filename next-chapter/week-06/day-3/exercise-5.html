The Detail Page

Exercise 5 / 5 . Level 3 . 35 min

Goal: click a card, land on a page showing that one opportunity in full. The list-and-detail pattern -- a feed of summaries that each link to a full record. Product pages, social posts, job boards, the docs I am reading right now: they all wear this shape. ReEntry Tech needs it because the board shows a title and a type, but the detail page is where someone actually reads the full description, sees the org, and decides whether to act.

The dynamic route

The folder name in brackets is the new convention. [id] means "match anything here and hand it to me as params.id": 

app/
  opportunities/
    page.js          -->  /opportunities       (the board)
    [id]/
      page.js        -->  /opportunities/7     (one listing)
// app/opportunities/[id]/page.js
import { prisma } from "@/lib/prisma";
import Link from "next/link";

export default async function OpportunityDetailPage({ params }) {
  const { id } = await params;

  const opportunity = await prisma.opportunity.findUnique({
    where: { id: parseInt(id, 10) },
    include: { org: true, tags: true },
  });

  if (!opportunity) {
    return (
      <div>
        <h1>Not Found</h1>
        <p>No opportunity with id {id}.</p>
        <Link href="/opportunities">Back to all</Link>
      </div>
    );
  }

  return (
    <div>
      <Link href="/opportunities">&larr; Back to all</Link>
      <h1>{opportunity.title}</h1>
      <span>{opportunity.type}</span>
      <p>{opportunity.description || "No description provided."}</p>
      {opportunity.org && <p>Posted by {opportunity.org.name}</p>}
      <div>
        {opportunity.tags.map((t) => (
          <span key={t.id} className="tag">{t.label}</span>
        ))}
      </div>
    </div>
  );
}
The two footguns that ate my first ten minutes

One: await params. In current Next.js params is a promise, so const { id } = await params; -- not params.id directly. Skip the await and you get a console warning and an id that is undefined-ish in a way that does not crash loudly, which is the worst kind of bug. Two: parseInt the id. The URL segment arrives as the string "7", but my Prisma id column is an Int. findUnique({ where: { id: "7" } }) is a type mismatch -- Prisma wants a number. parseInt(id, 10) with the explicit radix converts it. Both of these are the boundary between the URL (all strings) and the database (typed), and both bit me before I read the error closely enough to see they were boundary problems, not logic problems.

findUnique vs findMany

This is the first time I have reached for findUnique instead of findMany, and the distinction is exactly what it sounds like. findMany returns an array, possibly empty. findUnique returns one record or null, and it only works on a field the schema knows is unique -- the primary key, or anything marked @unique. So findUnique({ where: { id } }) is legal but findUnique({ where: { type: "job" } }) is not, because type is not unique and the query could match many. The return type tells you which to reach for: one thing or null, use findUnique; a list, use findMany.

The not-found branch is not optional, it is the whole point of a public URL

The board only ever links to ids that exist, so it is tempting to skip the if (!opportunity) check. But /opportunities/9999 is a public URL anyone can type, paste, or hit from a stale link after a listing gets deleted. Without the guard, opportunity is null and the next line -- opportunity.title -- throws "cannot read title of null," which Next.js turns into an ugly 500. The branch turns that into a calm "no opportunity with id 9999, here is the way back." This is the same lesson as Exercise 2's empty state, one level down: the user reached a real address, the answer is "nothing is here," and I should say so plainly instead of crashing.

Related listings off the same org (the stretch)

The detail page already loaded the org. Below the listing, I show the org's other postings -- a second query, scoped to the same org and excluding the one I am already looking at: 

const alsoFromOrg = await prisma.opportunity.findMany({
  where: {
    orgId: opportunity.orgId,
    NOT: { id: opportunity.id },
  },
  take: 4,
});

NOT: { id: opportunity.id } is "everything from this org except the current one," and take: 4 caps it. This is the relation paying off: because an Organization has many Opportunities, "more from this employer" is a one-line query, not a data-modeling project. For ReEntry Tech that is a genuinely useful surface -- someone interested in one posting from a verified partner is plausibly interested in that partner's others.

Checkpoint

Day 3 is done. The board lists, search filters, cards link, and each link opens a full record that handles the missing case and surfaces related listings. The read half of the app is real -- data flows schema to screen, with the joins, the empty states, and the type boundaries all handled deliberately. Tomorrow the arrows reverse: forms send data back, and the app starts holding things users put there instead of only what I seeded.
