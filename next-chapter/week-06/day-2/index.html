Day 2 -- Connect to Postgres + Prisma

NCD . WK6 . D2 . five exercises loaded . the code becomes a database

Yesterday Next.js gave React a server. Today that server gets a database. Every project I have shipped in this program so far stored its state in Cloudflare KV -- a key-value store. KV is wonderful for what it is: write a string, read it back by its key, done. But it has no schema, no types, no relations, and no way to ask "give me every active opportunity from verified organizations." You can fake all of that in application code, and I have, and it gets ugly fast. Today is my first real relational database in this program, and the bridge to it is an ORM.

An ORM -- Object-Relational Mapper -- is the layer between my JavaScript and the SQL the database actually speaks. I describe my data once, as code, and the ORM generates the tables and the queries. The one we use is Prisma. It has three moving parts that are worth keeping straight: the schema (schema.prisma, where I define models), the client (the generated, type-safe JS I call from server components), and Studio (a visual browser for the rows). The pitch is that the schema is the single source of truth and everything else is derived from it. That is the same instinct I liked about file-based routing yesterday: one declaration, no second copy to keep in sync.

The honest reframe for me: I already know SQL. I have written CREATE TABLE and SELECT ... WHERE by hand. So the question is not "how do I avoid SQL," it is "what do I give up and what do I gain by letting a tool generate it." What I gain is types -- a typo in a field name is a compile error, not a 2am production surprise -- and migrations I do not have to hand-write. What I give up is some control and a layer of indirection I now have to understand. Fine trade for an app this size. I want to know where the seams are, though, which is why I am writing down every footgun I hit today.

Lecture Notes -- Why an ORM Instead of Raw SQL

The argument from lecture, with my own gloss:

Problem with raw SQLWhat the ORM does
SQL is a second language; you context-switchYou stay in JS/TS
Typos surface at runtime, no autocompleteThe generated client is typed; typos are compile errors
Schema and code drift apart by handThe schema generates the client; one source of truth
String-built queries invite SQL injectionParameterized queries by default

The SQL injection point is the one I would underline for the cohort. It is not that Prisma is magic; it is that hand-concatenating user input into a query string is the original sin, and the ORM removes the temptation by never handing you the string.

Lecture Notes -- The Three Parts of Prisma

1. Schema (prisma/schema.prisma) -- where models live. Each model maps to a table, each field to a column.

model Opportunity {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  type        String   @default("job")
  createdAt   DateTime @default(now())
}

The attribute vocabulary I need today: Int / String / Boolean / DateTime for types, ? for nullable, @id for the primary key, @default(autoincrement()) for the serial id, @default(now()) for timestamps, @unique for a uniqueness constraint.

2. Client -- generated JS I import and call. No SQL.

const active = await prisma.opportunity.findMany({
  where: { active: true },
});

3. Studio -- npx prisma studio opens a spreadsheet-style view of the rows in the browser. Good for sanity-checking a seed.

Lecture Notes -- The Workflow (db push)
  1. Edit prisma/schema.prisma.
  2. npx prisma db push -- mirrors the schema onto the database.
  3. npx prisma generate -- regenerates the typed client (modern db push runs this for you).
  4. npx prisma studio -- eyeball the tables.

db push vs. migrate dev: db push just makes the database look like the schema. No history, no migration files. Perfect for the fast iteration I am doing this week. In Week 8 (deployment) we switch to prisma migrate dev, which writes migration files I commit to git, and prisma migrate deploy, which replays them in production. The one-line version: db push while the schema is still soft, migrate dev once it is real.

Lecture Notes -- Relations

A relation is a connection between models. One-to-many is the common case: an Organization has many Opportunities.

model Organization {
  id            Int           @id @default(autoincrement())
  name          String
  opportunities Opportunity[]   // the "many" side, a list
}

model Opportunity {
  id     Int          @id @default(autoincrement())
  org    Organization @relation(fields: [orgId], references: [id])
  orgId  Int            // the foreign key column
}

The [] means "many." The @relation(fields: [orgId], references: [id]) says "the orgId column on this row points at the id column on Organization." The orgId Int is the actual column that gets stored. Querying, Prisma does the join: include: { opportunities: true }.

Verbal Mini-Demo -- Walk Through Your Schema

Partner asked me to walk the ReEntry Tech schema and justify the choices. Three models. Organization is a partner org: name required, email with @unique because two orgs sharing an email is a data-entry mistake I want the database to reject, not something I check in app code, and verified Boolean @default(false) because a brand-new submission is untrusted until a human approves it. Opportunity is the posting: title required, description String? optional because a quick listing might not have a writeup yet, and type a string defaulting to "job."

The relations are the interesting part. Organization-to-Opportunity is one-to-many: the opportunities Opportunity[] on the org and the org plus orgId foreign key on the opportunity. One org posts many listings; each listing belongs to exactly one org. Opportunity-to-Tag is many-to-many: a "remote" tag applies to many opportunities, and one opportunity is both "remote" and "no-experience." So both sides carry a list and Prisma manages a hidden join table.

Partner's question: "What happens to the opportunities if I delete an organization?" Honest answer -- right now it would error, because the opportunities still hold an orgId pointing at a row that no longer exists and the foreign key constraint blocks the delete. To actually delete an org I would either delete its opportunities first or declare onDelete: Cascade on the relation. I have not added cascade yet because for ReEntry Tech I would rather deactivate an org than nuke every job it ever posted. That is a product decision the schema should reflect, and I will make it deliberately, not by default.

The Thing That Clicked Today

The schema is not documentation that describes the database. The schema is the database. That sounds like a small distinction until you feel it. For two years my mental model was: the database is the real thing, and any diagram or model file is a hopeful description of it that goes stale the moment someone runs an ALTER TABLE by hand. Prisma inverts that. I edit one file, run one command, and the database rearranges itself to match. The file is upstream of the truth, not a snapshot of it.

It is the same lesson as file-based routing yesterday and Pages Functions on Friday, three layers down. Routing: the folder structure is the router. Functions: the file in functions/api/ is the endpoint. Schema: the model in schema.prisma is the table. Each one takes a thing that used to be config you maintained separately and makes the declaration itself the source of truth. The pattern across all three is "stop describing the system, declare it, and let the tool derive the rest." That is the actual idea I am taking out of Week 6, and it is bigger than any one tool.
