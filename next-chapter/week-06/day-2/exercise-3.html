A Second Model with a Relation

Exercise 3 / 5 . Level 2 . 30 min

Goal: connect two models. Opportunities do not float free -- a partner organization posts them. So I add Organization and wire it to Opportunity as a one-to-many: one org, many opportunities.

The two models

model Organization {
  id            Int           @id @default(autoincrement())
  name          String
  email         String        @unique
  website       String?
  verified      Boolean       @default(false)
  createdAt     DateTime      @default(now())
  opportunities Opportunity[]
}

model Opportunity {
  id          Int          @id @default(autoincrement())
  title       String
  description String?
  type        String       @default("job")
  location    String?
  remote      Boolean      @default(false)
  active      Boolean      @default(true)
  createdAt   DateTime     @default(now())
  org         Organization @relation(fields: [orgId], references: [id])
  orgId       Int
}

Three new lines do the work. On Organization, opportunities Opportunity[] is the "many" side -- a virtual field, no column, just Prisma's handle for the list. On Opportunity, org Organization @relation(...) is the "one" side, and orgId Int is the real foreign-key column that stores the link. The @relation(fields: [orgId], references: [id]) spells out the wiring: my orgId points at Organization's id.

I also put @unique on the org email. Two organizations with the same contact email is a data-entry error, and I would rather Postgres reject it at insert than discover duplicates later. Constraints in the schema beat checks in the app code, because the schema cannot be bypassed by a bug in a code path I forgot about.

Push

$ npx prisma db push

Footgun: adding a required relation to a table that already has rows

My Opportunity table was empty, so this pushed clean. But it would NOT have if I had seeded first. Adding orgId Int -- a required column -- to a table with existing rows fails, because those rows have no orgId and Postgres cannot satisfy NOT NULL. db push would either error or offer to wipe the table. The fixes: make it optional (orgId Int?) first, backfill, then tighten it; or give it a default; or reset since this is throwaway prototype data. I got lucky on ordering this time. The lesson I am writing down: define relations before you seed, or be ready to do a backfill. This is exactly the kind of thing that is harmless in week 6 and a production incident in month 6.

Studio -- the link is visible

Two tables now. The Opportunity table has a new orgId column. In Studio that column renders as a clickable link to the related Organization row, and the Organization table shows an opportunities count per row. The relationship is not just conceptual; Studio walks it both directions. 

Organization (1) ----------< Opportunity (many)
  id                            id
  name                          title
  email  @unique               orgId  ---> Organization.id
  opportunities[]              org
Why is this one-to-many and not many-to-many?

Because a given opportunity is posted by exactly one organization -- it has a single owner. An org posts many listings, but a listing does not belong to several orgs at once. That is the definition of one-to-many, and it is why the foreign key lives on the Opportunity side (the "many" side always carries the key). The next exercise introduces a genuinely many-to-many relationship -- tags -- where that single-key model breaks down and Prisma needs a join table.

Checkpoint

Two connected tables. Prisma manages the join: I can ask for an org and include its opportunities, or an opportunity and include its org, and never write the SQL JOIN myself. Next: put data in them.
