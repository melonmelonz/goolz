Translate the Full Week 4 Model

Exercise 5 / 5 . Level 3 . 35 min

Goal: take the complete ReEntry Tech data model from Week 4 and make it real -- every table, every relation, sample data across all of them. The piece I have been building toward is the many-to-many: tags. An opportunity can be "remote" and "no-experience" and "transportation-provided" at once, and each of those tags applies to many opportunities. The single-foreign-key trick from Exercise 3 cannot express that.

Adding Tag (many-to-many)

model Opportunity {
  id          Int          @id @default(autoincrement())
  title       String
  description String?
  type        String       @default("job")
  location    String?
  remote      Boolean      @default(false)
  active      Boolean      @default(true)
  createdAt   DateTime     @default(now())
  org         Organization @relation(fields: [orgId], references: [id])
  orgId       Int
  tags        Tag[]
}

model Tag {
  id            Int           @id @default(autoincrement())
  name          String        @unique
  opportunities Opportunity[]
}

Both sides carry a list: tags Tag[] on Opportunity, opportunities Opportunity[] on Tag. No foreign key on either, because neither side owns the other. After db push, Studio shows a third table I never declared: _OpportunityToTag.

What is _OpportunityToTag?

The join table Prisma created for me. A many-to-many cannot live as a column on either side -- one opportunity has many tags and one tag has many opportunities, so neither row can hold a single foreign key. The standard relational answer is a third table where each row pairs one opportunity id with one tag id. "Warehouse Associate is remote" is one row; "Warehouse Associate is no-experience" is another. Prisma manages this implicit join table automatically. I have hand-built these as bridge tables in raw SQL before; here I wrote tags Tag[] and it appeared. If I needed extra columns on the relationship itself -- say, who added the tag and when -- I would promote it to an explicit join model, but I do not need that yet.

Seeding with connectOrCreate

Tags are shared across opportunities, so I cannot just create them inline the way I did with opportunities -- the second time I used "remote" it would try to create a duplicate and hit the @unique on name. The right tool is connectOrCreate: connect to the existing tag if it is there, create it if it is not. 

const tag = (name) => ({ where: { name }, create: { name } });

await prisma.organization.create({
  data: {
    name: "Second Chance Staffing",
    email: "hire@secondchancestaffing.org",
    verified: true,
    opportunities: {
      create: [
        {
          title: "Warehouse Associate",
          type: "job",
          location: "Newark, NJ",
          tags: {
            connectOrCreate: [
              tag("no-experience"),
              tag("transportation-provided"),
            ],
          },
        },
        {
          title: "Remote Data Entry",
          type: "job",
          remote: true,
          tags: {
            connectOrCreate: [
              tag("remote"),
              tag("no-experience"),
            ],
          },
        },
      ],
    },
  },
});

"no-experience" is created on the first opportunity and reused -- connected -- on the second. After the seed, the Tag table has each name exactly once, and _OpportunityToTag has the pairings. The little tag() helper just spares me retyping the where/create shape for every tag.

The piece for tomorrow: a single Prisma client

I am querying from Next.js server components tomorrow, and there is a well-known footgun I want handled before I get there. In development, Next.js hot-reloads on every save. If I do new PrismaClient() at module scope in a route, each reload makes a fresh client and opens a new pool of database connections. They pile up and eventually Neon refuses new connections. The fix is the standard global singleton -- create the client once and reuse it across reloads. lib/prisma.js: 

import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis;

export const prisma =
  globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma;
}
Why stash it on globalThis instead of just a module-level const?

Because hot reload throws away the module and re-evaluates it, so a plain module-level const is recreated every save -- which is the leak. globalThis survives the reload, so globalForPrisma.prisma ?? new PrismaClient() reuses the existing client instead of spawning another. I guard the assignment with NODE_ENV !== "production" because production does not hot-reload and I do not want to lean on a global there. This is the same instinct as a connection pool in any long-lived server: make the expensive resource once, share it. It maps directly onto how I think about a Worker holding a single binding rather than reconnecting per request.

Push, seed, verify

Four tables now: Organization, Opportunity, Tag, and the implicit _OpportunityToTag. The full Week 4 model for ReEntry Tech is a real database -- one-to-many from orgs to opportunities, many-to-many from opportunities to tags, seeded with data that looks like the actual app. Tomorrow it stops being a Studio curiosity and starts feeding API routes and pages.

What I would add next, deliberately not today

An Applicant / Application side -- people applying to opportunities -- which is another many-to-many with status on the relationship, so it would be an explicit join model, not implicit. And onDelete behavior on the org relation, decided per the product question from the verbal demo (deactivate, do not cascade-delete an org's history). I am noting these instead of building them because the assignment is to translate the Week 4 model, and bolting on speculative tables now would just be schema I have to maintain before I have a reason to. Build what the model says; add the rest when the feature needs it.
