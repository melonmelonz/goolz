Seed the Database

Exercise 4 / 5 . Level 2 . 30 min

Goal: fill the empty tables with sample data I can develop against. An empty database is useless for building UI -- tomorrow I read this data into Next.js pages, and I need rows to read. A seed script is a repeatable way to load them.

The script (ESM)

My Next.js project has "type": "module" in package.json, so the seed uses import, not require. Getting this wrong throws require is not defined in ES module scope, which is a confusing error if you do not know the cause. Here is prisma/seed.js: 

import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();

async function main() {
  // children before parents -- see the footgun below
  await prisma.opportunity.deleteMany();
  await prisma.organization.deleteMany();

  const goodwill = await prisma.organization.create({
    data: {
      name: "Second Chance Staffing",
      email: "hire@secondchancestaffing.org",
      verified: true,
      opportunities: {
        create: [
          {
            title: "Warehouse Associate",
            description: "Full-time, no experience required. Felony-friendly employer.",
            type: "job",
            location: "Newark, NJ",
          },
          {
            title: "CDL Class B Training",
            description: "Six-week commercial driver certification with job placement.",
            type: "certification",
            location: "Newark, NJ",
          },
        ],
      },
    },
  });

  const bridge = await prisma.organization.create({
    data: {
      name: "Bridge Forward Services",
      email: "intake@bridgeforward.org",
      verified: false,
      opportunities: {
        create: [
          {
            title: "Housing Navigation",
            description: "One-on-one help finding transitional housing.",
            type: "service",
          },
          {
            title: "Line Cook",
            description: "Restaurant partner hiring directly from the program.",
            type: "job",
            location: "Jersey City, NJ",
            remote: false,
          },
        ],
      },
    },
  });

  console.log("Seeded:");
  console.log(`  ${goodwill.name} (verified) -- 2 opportunities`);
  console.log(`  ${bridge.name} (unverified) -- 2 opportunities`);
}

main()
  .catch((e) => {
    console.error(e);
    process.exit(1);
  })
  .finally(async () => {
    await prisma.$disconnect();
  });

The nested create is the nice part. I create an Organization and its Opportunities in one call -- Prisma inserts the org, grabs the generated id, and stamps it onto each opportunity's orgId automatically. I never touch the foreign key by hand. That is the ORM earning its keep.

Register and run

In an ESM project the clean way to run a seed is to register it with Prisma. Top-level entry in package.json: 

"prisma": {
  "seed": "node prisma/seed.js"
}
$ npx prisma db seed

Seeded:
  Second Chance Staffing (verified) -- 2 opportunities
  Bridge Forward Services (unverified) -- 2 opportunities
Footgun: delete order with foreign keys

I delete opportunities before organizations. The reverse order errors. If I delete an organization while opportunities still point at it via orgId, Postgres refuses -- the foreign key constraint will not let me orphan child rows. Delete the children first, then the parent. This is the same constraint from Exercise 3 showing its other face: it protected me from a bad insert there, and it is protecting me from a bad delete here. It is not the ORM being fussy; it is the database guaranteeing that every orgId always points at a real org. I want that guarantee, so I order my deletes around it.

Why deleteMany at the top at all?

So the seed is idempotent. I will run it many times today while iterating on the schema. Without the clear-out, every run stacks another full set of rows on top of the last, and the unique email constraint on Organization would start throwing on the second run anyway. Clearing first means "run this script and the database is in exactly this known state," every time. That repeatability is the whole reason a seed script beats clicking rows into Studio by hand.

Verify in Studio

Two orgs, four opportunities. Clicking an opportunity's orgId jumps to its organization; clicking an org shows its opportunities list. The relationship I wired in Exercise 3 is now populated and walkable. Real data, real links.
