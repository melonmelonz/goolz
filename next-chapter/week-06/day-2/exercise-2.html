Define the First Model

Exercise 2 / 5 . Level 1 . 25 min

Goal: write a model, push it, and watch a real table show up in Studio. The brief uses a recipe example; I am building ReEntry Tech, so my first model is Opportunity -- the central thing in the app, a single posting that is either a job, a certification program, or a wraparound service.

The model

model Opportunity {
  id          Int      @id @default(autoincrement())
  title       String
  description String?
  type        String   @default("job")
  location    String?
  remote      Boolean  @default(false)
  active      Boolean  @default(true)
  createdAt   DateTime @default(now())
}

Every field choice here is deliberate. title is required because a listing with no title is not a listing. description is String? -- optional -- because a partner org might drop in a quick stub and fill the writeup later. type defaults to "job" since that is the most common posting. remote and active are booleans with sensible defaults so a new row is "not remote, currently active" unless told otherwise. createdAt stamps itself with @default(now()) so I never set it by hand.

Push it

$ npx prisma db push

Your database is now in sync with your Prisma schema.
Running generate... Generated Prisma Client in 78ms
Did I need to run prisma generate separately?

No. Modern db push runs prisma generate at the end automatically -- you can see "Running generate..." in the output above. I ran npx prisma generate once on its own anyway, just to watch what it does in isolation: it reads the schema and writes the typed client into node_modules/.prisma/client. That is the code my server components will import tomorrow. db push changes the database; generate changes the client. They usually run together, but they are two different jobs and it is worth knowing which is which.

Studio

$ npx prisma studio

Opened on localhost:5555. The Opportunity table is listed. Clicking it shows the columns -- id, title, description, type, location, remote, active, createdAt -- and zero rows. Empty is expected; I add data in Exercise 4. The point of this step was to confirm the model became a table, and it did.

This is the row I would have hand-written as CREATE TABLE "Opportunity" (...) with about nine lines of SQL and at least one typo. Instead I wrote nine lines of schema and the ORM emitted the SQL. The left column is the contract I maintain; the right column is the thing Prisma keeps in sync with it.

What does the ? actually change at the database level?

It flips the column between NOT NULL and nullable. title String becomes NOT NULL -- Postgres rejects an insert with no title. description String? allows NULL, so a row with no description is legal. This is the database enforcing my data rules, not my JavaScript hoping it remembered to. That is the part I want for ReEntry Tech: the integrity guarantee lives one layer below the app code that might have a bug.
