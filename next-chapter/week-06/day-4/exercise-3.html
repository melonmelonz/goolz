Wire the Full Loop

Exercise 3 / 5 . Level 2 . 35 min

Goal: connect the two halves so submitting the form inserts a row and the new listing appears -- the full create loop, form to fetch to route to database to UI. The mechanical part is swapping yesterday's console.log for a real fetch. The interesting part is the question I flagged at standup: how does the list find out a new row exists, and what does answering that cost the board's architecture.

The form makes a real request

// app/opportunities/create-form.js  (handleSubmit only)
import { useRouter } from "next/navigation";
// const router = useRouter();  inside the component

async function handleSubmit(e) {
  e.preventDefault();

  const res = await fetch("/api/opportunities", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title, description, type }),
  });
  const data = await res.json();

  if (!res.ok) {
    setError(data.error || "Something went wrong");
    return;
  }

  setTitle("");
  setDescription("");
  setType("job");

  if (onSuccess) onSuccess(data);   // path A: client state
  router.refresh();                 // path B: re-pull server data
}

I check res.ok before celebrating -- a 400 from a missing title is still a completed fetch, so res.ok (true only for 2xx) is what separates "saved" from "rejected with a message." On success I clear the fields back to their initial state, including the select back to "job", so the form is ready for the next entry instead of holding stale values.

The decision I sat on: onSuccess prepend vs. router.refresh

Two ways to make the new row show, and I wired both to feel them. Path A -- onSuccess: the form calls back to the page with the created row, the page prepends it to a useState array, React re-renders, the listing appears instantly with zero extra network. The cost: the board must hold the list in client state, which means the board becomes a client component and loses yesterday's server-side simplicity. Path B -- router.refresh(): tells Next.js to re-run the server render and re-pull the data, so a server-component board picks up the new row on its own. The cost: a round-trip to the server after every create, and a beat of latency before the row shows. Path A is faster and heavier; Path B is simpler and chattier.

Path A: the board as a client component

// app/opportunities/page.js  (client version)
"use client";

import { useState, useEffect } from "react";
import CreateOpportunityForm from "./create-form";

export default function OpportunitiesPage() {
  const [opportunities, setOpportunities] = useState([]);

  useEffect(() => {
    fetch("/api/opportunities").then((r) => r.json()).then(setOpportunities);
  }, []);

  function handleNew(created) {
    setOpportunities([created, ...opportunities]);
  }

  return (
    <div>
      <h1>Opportunities</h1>
      <CreateOpportunityForm onSuccess={handleNew} />
      {opportunities.map((o) => (
        <div key={o.id}>{o.title}</div>
      ))}
    </div>
  );
}

Look at what this costs. Yesterday this page was a server component that did await prisma.findMany() inline -- no fetch, no effect, no loading gap. To get the instant-prepend behavior, the whole page flips to "use client", the direct Prisma query becomes a useEffect + fetch through the API route, and the simplicity I praised on Day 3 is gone. This is the exact tradeoff the lecture warned about, and feeling it is the point: interactivity is not free, it is paid in client-side complexity.

What I'd actually ship: router.refresh on a server board

Given the choice, I keep the board a server component and use router.refresh(). For ReEntry Tech, a listing appearing a few hundred milliseconds after submit instead of instantly is a non-issue -- nobody is rapid-firing opportunity posts -- and in exchange I keep the page server-rendered, the data fresh from one source, and zero list-state to keep in sync with the database. Path A's instant prepend is the right call for something that feels like typing -- a chat, a comment thread, a live cart. A create form that fires occasionally is not that. I would rather pay one round-trip than carry a client-state copy of the list that can silently drift from what is actually in Postgres. The optimistic-update version is a real technique; it is just heavier than this form earns.

Test the loop

Load the board, fill the form, submit. The new opportunity shows up. Then the test that proves it is real: reload the page. The listing is still there, because it is a row in Neon, not a value in memory. That reload-survives moment is the whole arc of the day -- before today, anything not in my seed script vanished on refresh.

Checkpoint

Full loop closed. The app reads and writes; users put data in and it persists. I built both refresh paths, felt the server-to-client cost of the instant one, and decided router.refresh() on a server board is what I would ship here -- a decision, not a default. What is still missing is the wall: right now a one-space title or a novel-length one gets through. Next exercise.
