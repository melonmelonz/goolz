The POST Handler

Exercise 2 / 5 . Level 1 . 25 min

Goal: teach the existing route to accept a new opportunity. Yesterday's route.js only exported GET. Today I add POST right beside it -- same file, same URL, opposite verb -- so /api/opportunities both lists and creates depending on how you knock. This is the half I have done before in the notepad's KV save, so the new thing is small and specific: it writes to a real relational table now, and it returns the created row.

POST alongside GET

// app/api/opportunities/route.js
import { prisma } from "@/lib/prisma";
import { NextResponse } from "next/server";

// from yesterday
export async function GET() {
  try {
    const opportunities = await prisma.opportunity.findMany({
      orderBy: { createdAt: "desc" },
    });
    return NextResponse.json(opportunities);
  } catch (error) {
    return NextResponse.json(
      { error: "Failed to fetch opportunities" },
      { status: 500 }
    );
  }
}

// new today
export async function POST(request) {
  try {
    const body = await request.json();

    if (!body.title || body.title.trim() === "") {
      return NextResponse.json(
        { error: "Title is required" },
        { status: 400 }
      );
    }

    const created = await prisma.opportunity.create({
      data: {
        title: body.title.trim(),
        description: body.description?.trim() || "",
        type: body.type || "job",
      },
    });

    return NextResponse.json(created, { status: 201 });
  } catch (error) {
    return NextResponse.json(
      { error: "Failed to create opportunity" },
      { status: 500 }
    );
  }
}

Two exports, one file. Next.js routes by method automatically -- a GET to this path runs GET, a POST runs POST, and I never wrote a single line of "if method is...". That dispatch used to be my job in a Pages Function, where one handler switched on request.method. Here the function name is the method, which is cleaner and harder to get wrong.

body.title.trim() before testing, and ?. on the optionals

Two small things doing real work. First, I validate body.title.trim() === "", not just !body.title, because a title of " " -- three spaces -- is truthy and would sail past a bare falsy check, then store a listing that looks blank. Trim first, then test emptiness. Second, body.description?.trim() with the optional-chaining ?.: if description is missing entirely, body.description is undefined, and calling .trim() on undefined throws. The ?. short-circuits to undefined instead, and the || "" turns that into an empty string. So an absent optional field degrades to empty rather than crashing the whole create.

Why 201, not 200

GET returns 200 -- "here is what you asked for." POST returns 201 Created -- a more specific success that means "I made a new resource." It is not pedantry; a client can read 201 and know a row was created without inspecting the body, and tooling, caches, and logs treat the two differently. Returning the created row with the 201 also hands the client the database-assigned id and createdAt it did not have -- which is exactly what tomorrow's "redirect to the new detail page" needs. Send back the thing you made, with the code that says you made it.

Test it from the console

No form needed yet -- I can exercise the endpoint straight from the browser console, which is also the proof that the route is reachable by anything, not just my UI: 

fetch("/api/opportunities", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    title: "Forklift Certification -- evenings",
    description: "Two-week evening program, transportation provided.",
    type: "certification",
  }),
})
  .then((r) => r.json())
  .then((data) => console.log("created:", data));

The console logs the new row, id and createdAt filled in by the database. Then I open /api/opportunities (a plain GET) and the new listing is in the array, on top because of yesterday's orderBy desc. It survives a page reload because it is in Postgres now, not in memory -- which is the entire difference today makes.

Footgun: forget the Content-Type header and request.json() throws

If I drop headers: { "Content-Type": "application/json" }, the body still goes up, but the server does not know to parse it as JSON, and await request.json() throws -- which my try/catch turns into a 500 that reads "failed to create" and sends me hunting in the wrong place. The bug is not in the create; it is that the request never declared its content type. This is the exact pair the form will set for me in Exercise 3, but testing raw from the console means I set it by hand, and forgetting it once was a useful reminder of what the form is quietly doing.

Checkpoint

The endpoint creates. It reads a JSON body, refuses an empty title with a 400, inserts with Prisma, and returns the row with 201 -- and I proved all of it from the console before any form touched it. Both ends now exist independently: a form that captures (Exercise 1) and a route that persists (this one). Next they meet.
