Day 4 -- API Routes: CREATE

NCD . WK6 . D4 . five exercises loaded . the app starts holding what users give it

Yesterday the app could read. Every row it showed was a row I put there -- seed data, written from a script on my own machine. Today users can write. A form, a submit, data going up the wire, a row appearing in Postgres, the list refreshing to show it. That sounds like a small addition on top of yesterday and it is not. It is the line between a demo and an application. After today the database holds things I did not put there, which means I am now responsible for what gets in.

The honest reframe, same as yesterday: the POST handler itself is not new to me. The notepad I built two weeks ago has a functions/api/docs.js that takes a body, validates it, and writes to KV. So "read the request, validate, persist, respond" is a shape I know. What is new is everything around it. The React side -- controlled inputs, where every keystroke flows through state and back into the field -- I have only done badly before; my prototypes always go wonky here. And the part that genuinely reorganizes the page is that adding a form with state can force the whole page from a server component back to a client component, undoing exactly the simplicity I liked yesterday. That tradeoff is the spine of today.

There is also a fork in the road I want to name up front. Next.js offers Server Actions -- a way to run server code straight from a form with no separate API route at all, the "use server" directive doing what a whole endpoint used to. It is genuinely less code. I am deliberately not using it today. The traditional form-to-fetch-to-route-to-database path is the one that transfers to every backend I will ever touch -- it is just HTTP -- and I would rather own the mechanism before I let a framework hide it. Server Actions are Week 7. Today I build the loop by hand so I know what the shortcut is shortcutting.

Morning Warm-up -- What Fields Does Your Create Form Need?

What they are creating: a new Opportunity -- an org posting a job, a certification program, or a service.

The fields: title, description, type (a select: job / certification / service).

Required vs. optional: title required -- a listing with no title is not a listing. Type required but defaulted to "job," so the form is never blank. Description optional -- a quick post might not have a writeup yet, which is why I made the column String? yesterday.

Standup

What I did yesterday: built the read half. A GET route, a server-component board that queries Prisma inline, client-side search, styled cards in a reflowing grid, and a detail page per listing with a related-from-this-org section.

What I'm doing today: the create half. A controlled form, a POST handler on the same route, wiring the two so a submit inserts a row and the list updates, validation on both client and server, and a success state.

Where I'm stuck: not stuck, but I have a real design decision to make and I do not love either option. To get the new item to appear after submit, I can either lift the list into client state and prepend the returned row (fast, but the board becomes a client component again, undoing yesterday's server-side simplicity), or keep the board server-side and call router.refresh() to re-pull (keeps the simplicity, costs a round-trip per create). I am going to do both in the same form so I can feel the difference, then write down which I would actually ship.

Lecture Notes -- POST Receives, GET Returns

Same URL, different verb, opposite direction of data:

RequestMeansDirection
GET /api/opportunitiesgive me all opportunitiesdata comes out
POST /api/opportunitieshere is a new opportunitydata goes in

The URL names the resource, the method names the action -- that is REST, and it is the same model the notepad endpoints already follow. The body is where POST differs: it carries the new record as JSON, read server-side with await request.json().

Lecture Notes -- A POST Handler
// app/api/opportunities/route.js  (alongside GET)
export async function POST(request) {
  try {
    const body = await request.json();

    if (!body.title || body.title.trim() === "") {
      return NextResponse.json(
        { error: "Title is required" },
        { status: 400 }
      );
    }

    const created = await prisma.opportunity.create({
      data: {
        title: body.title.trim(),
        description: body.description?.trim() || "",
        type: body.type || "job",
      },
    });

    return NextResponse.json(created, { status: 201 });
  } catch (error) {
    return NextResponse.json(
      { error: "Failed to create opportunity" },
      { status: 500 }
    );
  }
}

Read the body, validate, prisma.create, return the new row with 201 -- the status code that specifically means "created," not just "ok." The status codes are not decoration; 400 is "your request was bad," 500 is "my server broke," 201 is "made the thing." A client can branch on those without parsing my prose.

Lecture Notes -- Controlled Inputs

The React form pattern that I have historically gotten wrong: every input's value is bound to state, and every keystroke writes back to that state.

const [title, setTitle] = useState("");

<input
  value={title}
  onChange={(e) => setTitle(e.target.value)}
/>

The input does not hold its own value -- React does. The field shows title, typing fires onChange, which calls setTitle, which re-renders with the new title, which the field shows. A loop, and React is the single source of truth for what is in the box. The payoff is that on submit I already have the values in state; I do not go digging them out of the DOM. e.preventDefault() in the submit handler stops the browser's default full-page reload so I can send the fetch myself.

Verbal Mini-Demo -- Walk Your Create Flow, Then Break It

Partner had me trace the whole loop pointing at code. Submit fires handleSubmit, which calls e.preventDefault() so the page does not reload, then fetch("/api/opportunities", { method: "POST", body: JSON.stringify(...) }). That lands in my POST handler, which does await request.json(), checks if (!body.title), calls prisma.opportunity.create, and returns the new row with 201. Back in the form, I read response.ok, clear the fields, and tell the page to show the new listing. Form to fetch to route to database to screen.

Then the fun half: they tried to break it. Empty title -- caught, "Title is required," because both my form and my handler check it. A single space -- this one I had to fix mid-demo, because " " is truthy, so !body.title passes and only title.trim() === "" catches it; good thing the handler trims before testing. A 5000-character title -- went straight in, because I had no max-length check yet, which is precisely the kind of gap this exercise exists to surface. Emoji and angle brackets in the description -- stored fine, and Prisma's parameterized queries meant the angle brackets were data, not an injection, which is the thing I underlined back on Day 2.

The question that landed: "What if someone skips your form entirely and POSTs from curl?" That is the whole argument for server-side validation. My form's checks are a courtesy to a cooperating user. Anyone can bypass the browser -- curl, Postman, the console -- and hit the route raw. The handler is the only check that actually runs no matter how the request arrives, so the handler is where the real validation has to live. The client check is for speed; the server check is for safety.

The Thing That Clicked Today

Validation on both sides felt like duplication until I saw it as two different jobs wearing the same code. The client check exists to be kind -- instant feedback, no round-trip, "title is required" the moment you blur the field. It assumes a cooperating user in a browser and optimizes their experience. The server check assumes nothing. It assumes the request might come from curl, from a script, from someone who read my JavaScript and decided to skip it, from a future bug in my own client that sends garbage. Same rule -- "title cannot be empty" -- but one is a hint and the other is a wall. They are not redundant; they are aimed at different threats.

That reframed something I have been sloppy about for years. I used to think "validate the input" was one task you did once, ideally close to the user where the error message is friendliest. It is two tasks. The friendly one and the load-bearing one, and if you only do the friendly one your database is one curl command from garbage. For ReEntry Tech that is not abstract -- this data is about people's actual reentry, jobs and certifications they will act on, posted by orgs I marked verified. The wall has to be on the server because the server is the only place the wall cannot be walked around. The form is hospitality. The handler is the lock.
