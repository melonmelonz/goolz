Build the Form (Controlled Inputs)

Exercise 1 / 5 . Level 1 . 30 min

Goal: a form that captures every field of a new Opportunity and proves it captured them -- no network yet, just the React side. I am isolating this on purpose. Controlled inputs are the part of React I have historically fumbled, so I want the form working and observable before I add the fetch, the route, and the database on top. Get the input loop right against a console log, then build the rest on something I trust.

The component

// app/opportunities/create-form.js
"use client";

import { useState } from "react";

export default function CreateOpportunityForm() {
  const [title, setTitle] = useState("");
  const [description, setDescription] = useState("");
  const [type, setType] = useState("job");

  function handleSubmit(e) {
    e.preventDefault();
    console.log("payload:", { title, description, type });
    alert("Submitted -- check the console.");
  }

  return (
    <form onSubmit={handleSubmit}>
      <label>Title *</label>
      <input
        type="text"
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="e.g. Warehouse Associate -- no experience"
        required
      />

      <label>Description</label>
      <textarea
        value={description}
        onChange={(e) => setDescription(e.target.value)}
        rows={3}
      />

      <label>Type</label>
      <select value={type} onChange={(e) => setType(e.target.value)}>
        <option value="job">Job</option>
        <option value="certification">Certification</option>
        <option value="service">Service</option>
      </select>

      <button type="submit">Add Opportunity</button>
    </form>
  );
}

"use client" at the top because a form is interactive -- it holds state and responds to input, which is the definition of a client component. Three pieces of state, one per field. Each input is bound: value reads the state, onChange writes it. The field never holds its own value; React does, and the input is just a view of it.

The select defaults to "job" and that matters more than it looks

I initialized type to "job", not "". A select with no matching option shows a blank or the first option while state says something else, and you get the classic "I never touched the dropdown so my value is empty" bug on submit. By seeding state to a real option, the form is valid from the first render -- the user can submit without opening the dropdown and still get a sensible type. This mirrors the schema, where type has @default("job"). Form default and column default agreeing is one less surprise.

Footgun I have hit before: controlled input with value but no onChange

If I write value={title} and forget onChange, the field is frozen -- React owns the value, nothing updates it, and typing does nothing while the console screams about a controlled input without an onChange handler. The inverse is just as bad: onChange with no value makes an uncontrolled input that React does not track. It is both or neither. This is exactly where my old prototypes went wonky -- I would half-wire a field and then chase a "why can't I type" ghost. Both halves, every field, no exceptions.

Drop it on the page to see it

Test it

Fill the fields, submit, open the console (right-click, Inspect, Console). The payload object is there with exactly what I typed -- title, description, and the selected type. e.preventDefault() is doing its quiet job: without it the form would do a native submit and reload the page, blowing away the console log before I could read it. With it, the page stays put and I own the submit.

Checkpoint

The form captures clean data and I can watch it do so. No fetch, no route, no database -- and that is deliberate. The React half is proven against a log, so when the next exercise adds the network I will know any new bug is in the wiring, not the form. Next: the endpoint that will receive this payload.
