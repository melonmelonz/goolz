Success State

Exercise 5 / 5 . Level 3 . 25 min

Goal: close the loop with feedback. Right now a successful submit clears the fields and the row appears, but the form says nothing -- the user is left guessing whether it worked. This exercise adds the small set of states that make the form feel finished: a loading state that prevents double-posts, a confirmation message, and optionally a redirect to the new listing. None of it is hard; all of it is the difference between a form that works and a form that feels trustworthy.

Loading state -- the guard against double submits

const [loading, setLoading] = useState(false);

async function handleSubmit(e) {
  e.preventDefault();
  // ...client validation...
  setLoading(true);
  try {
    const res = await fetch(/* ... */);
    // ...handle response...
  } finally {
    setLoading(false);
  }
}

<button type="submit" disabled={loading}>
  {loading ? "Saving..." : "Add Opportunity"}
</button>
This is the state I'd have skipped, and it is the most important one

A success message is nice. The disabled={loading} guard is the one that prevents a real bug. Network requests take time, and an impatient user clicks Submit twice -- or five times -- before the first one returns. Without the guard, that is two or five identical opportunities in the database, and now I am writing a dedupe script. Disabling the button the instant the request starts makes the second click impossible. The finally block re-enables it whether the request succeeded or threw, so a failed submit does not leave the button stuck forever. I have lived the duplicate-rows version of this before; the fix is three lines and I will never not write them again.

Success message

const [success, setSuccess] = useState(false);

// after a confirmed 201:
setSuccess(true);
setTimeout(() => setSuccess(false), 3000);

// in the JSX:
{success && <p className="ok">Opportunity posted.</p>}
{error && <p className="err">{error}</p>}

The message shows on success and clears itself after three seconds, so the form does not accumulate stale confirmations as the user posts several listings. Success and error are separate state, never both true -- I set error("") at the top of submit and only flip success after a confirmed 201, so the two messages cannot fight over the same spot.

The redirect alternative

import { useRouter } from "next/navigation";
const router = useRouter();

// after a confirmed 201, instead of staying:
router.push(`/opportunities/${data.id}`);
Stay-and-confirm vs. redirect is a product decision, not a code one

Two valid endings. Stay and confirm: the user remains on the board, sees "posted," and can immediately add another -- right for bulk entry, like an org loading ten postings in a sitting. Redirect to the detail page: router.push to /opportunities/${data.id} sends them to the listing they just made -- right when each create is a deliberate, one-off act they want to review. This is exactly why Exercise 2 returned the created row with its id: I cannot redirect to a record whose database id I do not have, and the 201 body is where that id comes from. For ReEntry Tech I would let a verified org bulk-post (stay and confirm) and redirect on the rare admin-creates-one path. Same two lines of code; the choice is about who is using the form and why.

The full form state set

Counting them up, the finished form holds: a value per field, error, success, and loading. That is the honest cost of a good form -- six-ish pieces of state, each earning its place. Compared to Day 3's server-component read page, which had zero state, this is the price of letting users write instead of only read. Worth it, but I want to see it plainly: interactivity is paid in state, and every state is a thing that can be wrong, so I keep them minimal and never store what I can derive.
