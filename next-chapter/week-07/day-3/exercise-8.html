A Real Feature: AI-Drafted Descriptions

Exercise 8 / 9 . stretch . Level 3 . 45 min

Goal: an AI feature a user would actually want, integrated where the app already lives -- not a chat page nobody visits. The candidate picked itself: back on W6D4 I made description optional because "a quick post might not have a writeup yet." That design shrug is now a product gap the model can fill. Orgs post fast, listings land blank, and a blank description helps nobody searching the board. So the create form grows a button: Draft with AI.

The route -- its own endpoint, its own persona

// app/api/ai/draft-description/route.js
export async function POST(request) {
  try {
    const { title, type, location } = await request.json();
    if (!title?.trim()) {
      return NextResponse.json(
        { error: "Title is required to draft" }, { status: 400 });
    }

    const response = await openai.chat.completions.create({
      model: "gpt-5-mini",
      messages: [
        { role: "system",
          content: `You draft listing descriptions for a reentry
opportunity board. 2-3 sentences, plain language. Say what the
opportunity is and what a person would actually do. No corporate
buzzwords, no "exciting opportunity," no exclamation points.
NEVER invent specifics that were not provided -- no pay rates,
no schedules, no requirements you were not told about.` },
        { role: "user",
          content: `Draft a description.\nTitle: ${title}\nType: ${type}\nLocation: ${location || "not specified"}` },
      ],
      temperature: 0.8,
    });

    return NextResponse.json(
      { description: response.choices[0].message.content });
  } catch (error) {
    console.error("Draft error:", error);
    return NextResponse.json(
      { error: "Could not draft a description" }, { status: 500 });
  }
}
The NEVER-invent line is the feature's whole ethics

First draft of this system message lacked it, and the model immediately decorated a forklift-cert test with "$18-22/hr" and "flexible scheduling" -- fabricated, fluent, and exactly the kind of detail someone would plan around. That is Exercise 6's never-speculate principle resurfacing with stakes: on this board a hallucinated wage is not filler, it is a broken promise the org never made. Constraint added, re-tested five titles, zero invented specifics. The drafts got blander, and blander is correct -- the org adds the real specifics by editing, which is the next design decision down.

The form side -- suggestion, never verdict

// in the create form, next to the description textarea
<button type="button" onClick={draftDescription}
        disabled={drafting || !title.trim()}>
  {drafting ? "Drafting..." : "Draft with AI"}
</button>

// draftDescription POSTs title/type/location, then:
setDescription(data.description);   // lands IN the textarea, editable

Three deliberate choices. The button disables until a title exists, because the route requires the one fact everything hangs on. The draft lands in the controlled textarea, not the database -- the org reads it, edits it, owns it, and only submit persists anything; nothing AI-written enters Postgres unread by a human. And type="button", learned the annoying way: the first version submitted the whole form on click because a button inside a form defaults to type="submit" -- a 2014-vintage HTML footgun firing in an AI feature, which felt about right for this course.

Checkpoint

End to end: typed "Peer Support Specialist," type certification, clicked Draft -- two seconds, then a plain, accurate, unhyped description appeared in the textarea, which I trimmed by a sentence and submitted. Row in Postgres carries the human-edited version. Loading and error states wired; the failure path drops a quiet "could not draft -- write it manually" note under the field and leaves the form fully usable, because the AI is an accelerant here, never a dependency. This is the first thing I have built this week that I would show an actual partner org without preamble.
