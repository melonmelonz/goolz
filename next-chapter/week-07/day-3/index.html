Day 3 -- Third-Party APIs + the OpenAI API

NCD . WK7 . D3 . nine exercises loaded . the app stops talking to itself

Until this morning, ReEntry Tech was a closed loop: my frontend calls my routes, my routes call my database, everything in the conversation is mine. Today the loop opens. The app reaches out to servers I do not own, pulls back data I did not create, and folds it into what it shows. And the skill on offer is deliberately not "how to use the Weather API" -- it is how to open any API's documentation, find the same four things every API doc contains, and make the call. The four things: base URL, endpoints, authentication, response format. That is the whole literacy.

The course's framing device is good enough that I want to write it down before the day proves it: the OpenAI API -- the engine under ChatGPT -- is just another third-party API. Base URL, key, route through your own server, handle the errors. The same pattern that fetches a random dog photo fetches a completion from the model I have been pair-programming with for seven weeks. So the day runs generic-skill first, marquee example second, and by afternoon my own code is sending prompts to the same engine that has been on the other side of my terminal all along. There is something pleasingly circular about that.

One pattern rules the whole day: frontend to MY route to the external API. Never frontend straight to the external API. Three reasons, and I can now recite them cold -- the key stays on the server where the browser cannot leak it; CORS never enters the conversation because server-to-server requests do not trigger it; and when the external service fails, my route decides what the user sees instead of some other company's error JSON. Every production app does it this way. As of today, so does mine.

Morning Lab -- API Scavenger Hunt

The two URLs: api.chucknorris.io/jokes/random and dog.ceo/api/breeds/image/random, both opened raw in the browser. Both return JSON, not HTML -- no markup, no styles, just a data structure with the payload in a field.

What they have in common vs. a normal URL: a normal URL returns a page for a human; these return data for code. The browser is the wrong audience and renders them as plain text shrugging. The OpenAI API answers the same way -- raw JSON, completion nested inside -- and the whole day is about being the code these responses were designed for.

Lecture Notes -- The Four Things Every API Doc Tells You
ThingExample
base URLhttps://api.open-meteo.com/v1
endpoints/forecast, /weather -- what you can ask for
authenticationnone / key in query param / key in header / bearer token
request + response formatwhat you send, what JSON comes back

Open the docs, find these four, and you can make the call -- that is the skill, transferable to every API including the one with the AI behind it. The three auth patterns ascend in seriousness: key in the URL (hobby tier), key in a header (production), bearer token in the Authorization header (OAuth-land, and what the OpenAI SDK quietly does for you).

Lecture Notes -- External APIs Fail in Ways Your Own Code Cannot

Down, slow, rate-limited (429), key revoked, or the format changed under you. Always try/catch, always check response.ok, and decide what your user sees for each failure -- because "their server broke" and "my server broke" deserve different status codes (503 vs 500) and different sentences. Rate limits get respected by not calling on every keystroke, caching what does not change, and reading the limit headers. None of this is exotic; it is the same defensive posture as validating form input, pointed outward.

Lecture Notes -- Anatomy of an OpenAI Call
const response = await openai.chat.completions.create({
  model: "gpt-5-mini",        // fast + cheap; upgrade only if quality demands
  messages: [
    { role: "system", content: "who the AI is and how it behaves" },
    { role: "user",   content: "the actual question" },
  ],
  temperature: 0.7,           // 0 deterministic, 1 creative
});
const text = response.choices[0].message.content;

Tokens are the meter: roughly 0.75 words each, billed on prompt AND response. gpt-5-mini runs $0.25 per million in, $2 per million out -- a typical call costs two hundredths of a cent, which is nothing until an accidental loop makes it something. Spending limit set at $5 before I wrote a line of code. The system message is the most powerful parameter in the call -- same user question, different system message, unrecognizably different answer -- and it is where today's app-shaping actually happens.

Lecture Notes -- The Key Is a Credit Card

The OpenAI key bills my account directly, which makes it the same hygiene as every key only with sharper teeth: lives in .env, which is in .gitignore; read only in server-side code; never, ever prefixed NEXT_PUBLIC_, which would helpfully ship it to every browser. .env.example carries placeholders so the repo documents what keys exist without containing any. And the one operational gotcha that cost me ten minutes today: Next reads .env at startup, so a key added to a running dev server does not exist until the restart.

Verbal Mini-Demo -- The Data-Flow Pattern, Out Loud

Took Option 1. Pointed at app/api/advice/route.js on screen and walked it: the board never talks to adviceslip.com -- it fetches my route, my route runs on the server, makes the outbound call, reshapes the response, and hands back only what my UI needs. The three problems this solves, recited with the why: key security, because anything a browser can read a user can read, and my OpenAI key bills my card; CORS, because the browser's cross-origin rules apply to browsers and my server is not one; error handling, because when their API dies my route returns my 503 with my sentence instead of letting their failure format leak into my UI. What would break going direct from a client component: the key ships in the bundle, CORS blocks half the calls anyway, and every error page belongs to someone else.

Partner's follow-up: "what status do you return if the external key is invalid?" Good one -- the external API says 401, but parroting 401 to my frontend implies my user is unauthenticated, which is false and would trip auth handling that has nothing to do with this. My route logs the real 401 for me and returns a 502-flavored "external service misconfigured" to the page. The status code is part of the reshaping, not something you pass through raw. I had to think for a second on that one, which is how I know the question was worth asking.

The Thing That Clicked Today

The demystification was the headline. Seven weeks of treating the AI as the thing on the other side of the terminal, and today it became a POST request I wrote myself: a URL, a key, a JSON body, a response with the text nested in choices[0].message.content. Every AI feature in every product I use -- the autocomplete, the summarizers, the chat bubbles -- collapsed into the same shape as the dog-photo API the moment my own route returned a completion. The engine did not get smaller, but the mystery did, and those turn out to be different things.

The second click had teeth. Exercise 7 put my own database rows into the system message, and because my rows are written by whoever posts a listing, I got to run a prompt injection against myself and watch it land. The fix-shaped lessons -- user input stays in the user role, database text is untrusted the moment anyone else can write it -- matter less than the posture change: the model reads everything in the context window with the same credulity, and "data" versus "instructions" is a distinction I care about that the model does not. I have been on the trusting side of that window for seven weeks. Today I saw what it looks like from the other side, on a board meant for people who can least afford to be lied to by it.
