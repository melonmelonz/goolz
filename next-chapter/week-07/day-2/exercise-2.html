UPDATE in the UI

Exercise 2 / 6 . Level 1 . 35 min

Goal: a user can edit a listing. The action already exists and has five green tests; this exercise is the UI around it. The lab offered two paths -- wire the Server Action (Path A) or build a parallel PUT-route flow Week 6 style (Path B) -- and I took A, because the lecture's edit-page example for Path B is a client component juggling two useStates and a useEffect fetch just to pre-fill a form, and the Server Action version makes almost all of that evaporate.

First: the action learns the rest of the fields

Exercise 1's action only updates title; a real edit form needs description and type too. Tests first, still: extended the first test's assertion to expect all three fields in data, watched it go red, then widened the action. Red to green took two minutes, and the suite watched the whole thing.

The edit page -- a server component, start to finish

// app/opportunities/[id]/edit/page.js
import { prisma } from "@/lib/prisma";
import { notFound } from "next/navigation";
import { updateOpportunity } from "../../actions.js";

export default async function EditOpportunityPage({ params }) {
  const { id } = await params;           // Next 15+: params is a Promise
  const opp = await prisma.opportunity.findUnique({
    where: { id: parseInt(id) },
  });
  if (!opp) notFound();

  return (
    <main>
      <h1>Edit listing</h1>
      <form action={updateOpportunity}>
        <input type="hidden" name="id" value={opp.id} />

        <label>Title</label>
        <input name="title" defaultValue={opp.title} required />

        <label>Description</label>
        <textarea name="description" defaultValue={opp.description ?? ""} />

        <label>Type</label>
        <select name="type" defaultValue={opp.type}>
          <option value="job">Job</option>
          <option value="certification">Certification</option>
          <option value="service">Service</option>
        </select>

        <button type="submit">Save changes</button>
      </form>
    </main>
  );
}
Where the lecture's useEffect went

The Path B example pre-fills the form by mounting a client component, firing a fetch to GET /api/opportunities/[id], and copying the response into state -- loading flash included. A server component does not have that problem, because it runs where the database is: query Prisma inline, drop the values into defaultValue, and the HTML arrives at the browser already filled in. No flash, no fetch, no state. defaultValue instead of value is the other half of the trick -- uncontrolled inputs, because nothing on this page needs to react per-keystroke. React renders the starting value and gets out of the way; the form data goes straight to the action on submit.

The redirect after save

One real addition to the action: after a successful update it now ends with redirect("/opportunities") from next/navigation, so saving lands you back on the board. The gotcha I hit: redirect works by throwing a special control-flow error, so it cannot live inside the action's try block or my own catch eats the navigation. It goes after. The test suite caught nothing here because the tests mock next/navigation too -- noted honestly: this seam is verified by hand, not by Vitest.

The edit link on each card

// in the board's card render
<Link href={`/opportunities/${opp.id}/edit`}>Edit</Link>

A link, not a button with a handler -- the board stays a server component, untouched.

Checkpoint

Clicked Edit on the Forklift Certification listing, form arrived pre-filled, changed the description, saved. Landed on the board with the new text showing -- revalidatePath did the refresh, no router.refresh() in sight. Checked Postgres directly out of residual distrust: row updated. The full flow is form to action to Prisma to revalidate to redirect, and the only client-side JavaScript involved is whatever React ships to hydrate a form that would honestly work without it. The suite from Exercise 1 still passes, which after an afternoon of edits to the same file is not nothing.
