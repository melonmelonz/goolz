Tests First -- Spec Out UPDATE Before It Exists

Exercise 1 / 6 . Level 2 . 40 min

Goal: write the failing tests for updateOpportunity before the function -- or even its file -- exists, then have the AI implement against them. This is yesterday's Pattern 2 pointed at a real mutation. The file app/opportunities/actions.js does not exist when the test file imports from it, and that is not a problem, that is the point. The test file is the spec, and the spec comes first.

The setup -- yesterday's mock, two additions

// app/opportunities/actions.test.js
import { test, expect, vi, beforeEach } from "vitest";

vi.mock("@/lib/prisma", () => ({
  prisma: { opportunity: { findMany: vi.fn(), update: vi.fn() } },
}));

// Server Actions call revalidatePath; outside Next that import
// has no request context to work with, so it gets a fake too.
vi.mock("next/cache", () => ({ revalidatePath: vi.fn() }));

import { updateOpportunity } from "./actions.js";
import { prisma } from "@/lib/prisma";

beforeEach(() => { vi.clearAllMocks(); });
Two mocks, two different reasons

The Prisma mock is the same one as yesterday with update added next to findMany -- same hoist rules, fake defined inline in the factory. The next/cache mock is new and exists for a different reason: I am not asserting anything about it, I just need the import to not explode when the action calls revalidatePath outside of a real Next request. One mock is a test double I interrogate; the other is a stub I silence. Worth keeping those two jobs distinct in my head.

Four failing tests

function form(fields) {
  const fd = new FormData();
  for (const [k, v] of Object.entries(fields)) fd.set(k, v);
  return fd;
}

test("updates a listing title for a valid id", async () => {
  prisma.opportunity.update.mockResolvedValue(
    { id: 1, title: "Line cook (2nd shift)", type: "job" });

  await updateOpportunity(form({ id: "1", title: "Line cook (2nd shift)" }));

  expect(prisma.opportunity.update).toHaveBeenCalledWith(
    expect.objectContaining({
      where: { id: 1 },
      data: expect.objectContaining({ title: "Line cook (2nd shift)" }),
    }));
});

test("returns the updated row", async () => {
  const updated = { id: 1, title: "Line cook", type: "job" };
  prisma.opportunity.update.mockResolvedValue(updated);

  const result = await updateOpportunity(form({ id: "1", title: "Line cook" }));
  expect(result).toEqual(updated);
});

test("rejects when the listing no longer exists", async () => {
  prisma.opportunity.update.mockRejectedValue(
    Object.assign(new Error("Record not found"), { code: "P2025" }));

  await expect(
    updateOpportunity(form({ id: "9999", title: "whatever" }))
  ).rejects.toThrow();
});

test("touches exactly one row, scoped to the right id", async () => {
  prisma.opportunity.update.mockResolvedValue({ id: 1, title: "x" });

  await updateOpportunity(form({ id: "1", title: "x" }));

  expect(prisma.opportunity.update).toHaveBeenCalledTimes(1);
  expect(prisma.opportunity.update).toHaveBeenCalledWith(
    expect.objectContaining({ where: { id: 1 } }));
});

Ran the suite. RED across the file -- the import alone fails it, since actions.js does not exist. Four red tests and a missing file is a complete, unambiguous statement of what I want built. Also a small pleasant surprise: FormData just works in Node-run Vitest, no browser, no polyfill -- it has been a global since Node 18. The little form() helper keeps the tests readable, because four copies of set-set-set was noise.

What the fourth test is really guarding

Tests one and two check outputs. Test four checks the ask -- same species as yesterday's orderBy assertion. An update that hits the wrong where clause is the scariest bug in this file: it does not error, it does not look wrong in the UI you are staring at, it just quietly rewrites somebody else's listing. toHaveBeenCalledTimes(1) plus the exact where is the cheapest insurance available against the worst failure available.

Hand the red to the AI

The prompt was the tests, nearly verbatim: "Here are my failing Vitest tests for an UPDATE Server Action. Write app/opportunities/actions.js to make them pass. It uses Prisma via @/lib/prisma. Don't add features beyond what the tests describe." What came back: 

// app/opportunities/actions.js
"use server";

import { prisma } from "@/lib/prisma";
import { revalidatePath } from "next/cache";

export async function updateOpportunity(formData) {
  const id = parseInt(formData.get("id"));
  const title = formData.get("title");

  const updated = await prisma.opportunity.update({
    where: { id },
    data: { title },
  });

  revalidatePath("/opportunities");
  return updated;
}

GREEN, all four, first try -- second day in a row that a precise spec produced a correct implementation on the first attempt, which is starting to look less like luck and more like a law.

Refactor -- the test the spec forced me to add

Staring at parseInt(formData.get("id")): if the hidden input is ever missing, get returns null, parseInt(null) is NaN, and Prisma gets where: { id: NaN }. I wrote the failing test first -- expect a NaN id to reject before Prisma is ever called -- watched it red, then added the guard: 

const id = parseInt(formData.get("id"));
if (Number.isNaN(id)) throw new Error("Invalid opportunity id");

Plus one more assertion in that test: expect(prisma.opportunity.update).not.toHaveBeenCalled() -- garbage gets stopped at the door, not in the database. Five green. Suite stayed green through the whole refactor, which is the entire advertised benefit, experienced live.

Checkpoint

Five passing tests and a working updateOpportunity that has never once been run against the real database -- and does not need to be, yet. Reflection, three sentences as assigned: writing the tests first absolutely changed what I built, because the P2025 and NaN cases would not have occurred to code-first me until they happened. The tests forced me to decide what failure even means for this function before I wrote a line of it. And the function the AI wrote was boring, which is the highest compliment available -- all the interesting decisions had already been made, by me, in the spec.
