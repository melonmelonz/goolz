Today also pays off a debt I deliberately took on. That was the right call and today is the payoff -- I know exactly what the shortcut is shortcutting. CREATE stays as it is, fetch and POST, because it works and because that pattern is portable to every backend on earth. The second half of the day is documentation, and I am trying not to treat it as the vegetables. And the comments argument is the same argument as yesterday's tests -- the AI reads my project to write code for it, and a comment that says why is context the model cannot derive from the code alone. WHAT is in the code. WHY is only in my head until I write it down.

Morning Lab -- CRUD Quick-Check

What CRUD stands for, and what I have: Create, Read, Update, Delete. The board has the first two.

Where CREATE happens: the controlled form posts to the POST handler in app/api/opportunities/route.js -- validate, prisma.opportunity.create, return 201.

Where READ happens: two places. The board at app/opportunities/page.js is a server component querying Prisma inline, and GET on the same API route serves it as JSON -- the handler I put under test yesterday.

Pre-class question -- which page gets the buttons: the board. Edit and Delete live on each listing card, because that is where the listing is in front of you. Detail page gets them too, eventually. Delete gets a confirmation; edit does not need one, because an edit can be re-edited and a delete cannot be un-deleted.

Lecture Notes -- UPDATE Has Five Parts, DELETE Has Five Parts
UPDATEDELETE
edit button on the itemdelete button on the item
form pre-filled with current dataconfirmation -- "are you sure?"
the mutation requestthe delete request
prisma.updateprisma.delete
the page reflects the changethe item disappears

The shape is identical; the stakes are not. A bad update is recoverable -- edit it again. A bad delete is gone. That asymmetry is why every production app on earth -- Gmail, GitHub, all of them -- puts a dialog in front of delete and nothing in front of edit. The dialog is not politeness, it is the only undo this operation has.

Lecture Notes -- params Is a Promise Now
// app/api/opportunities/[id]/route.js -- Next.js 15+
export async function PUT(request, { params }) {
  const { id } = await params;   // MUST await -- params is a Promise
  ...
}

Dynamic-route params stopped being a plain object in Next 15. Every Next 14 example online does params.id directly, and that pattern now warns in dev and breaks production builds. Same rule for page components -- a client component unwraps it with React's use(params). Worth burning in, because this is exactly the kind of thing an AI trained on a million Next 14 tutorials will confidently get wrong, and yesterday taught me what to do about confident-and-wrong: put a test in front of it.

Lecture Notes -- Server Actions, the Four Moving Parts
// app/opportunities/actions.js
"use server";                              // part 1 -- the directive

export async function deleteOpportunity(formData) {
  const id = parseInt(formData.get("id")); // part 3 -- named inputs arrive as FormData
  await prisma.opportunity.delete({ where: { id } });
  revalidatePath("/opportunities");        // part 4 -- re-fetch the route's data
}

// in the page -- part 2: the form points at the function
<form action={deleteOpportunity}>
  <input type="hidden" name="id" value={opp.id} />
  <button type="submit">Delete</button>
</form>

No fetch, no JSON serialization, no useState plumbing, and -- the part that matters for my board -- no "use client" needed, so the page stays a server component. I went looking for the hidden wire and found it: Next compiles the action into a real POST endpoint behind the scenes and the form submits to it. It is not magic, it is codegen. The HTTP is still there; the framework just writes it for me. Knowing that is what lets me trust it.

revalidatePath() is the server-side cousin of the router.refresh() I used after CREATE -- it tells Next the data for that route is stale, so the next render re-pulls from the database. That replaces the whole "how does the list update" decision I agonized over on W6D4.

Verbal Mini-Demo -- UPDATE Out Loud, DELETE Under Attack

Walked my partner through the UPDATE flow end to end, pointing at files. Edit link on the card in app/opportunities/page.js, which routes to app/opportunities/[id]/edit/page.js -- a server component, so the pre-fill is not a useEffect fetch, it is Prisma queried inline and the row's values dropped into defaultValue on uncontrolled inputs. Save submits the form whose action is updateOpportunity; Next carries the FormData to the server function, Prisma updates the row, revalidatePath marks the board stale, the redirect lands on a board that re-pulled. The sentence that proved I understood it: at no point did I write a fetch, and yet an HTTP POST absolutely happened -- I just did not have to be the one to write it.

Then they tried to break my DELETE, which is the better half of the activity. Delete then Cancel: listing stays, no request fired -- confirmed in the network tab, which is the part that matters, because a cancel that still fires the request is a lie. Delete then OK: row gone, board refreshed. The double-click: second confirm fires, second delete throws P2025 on a row that is already gone -- caught, logged, no crash, though I noted the button should really disable itself after the first click. Their follow-up question: "what if the API call fails entirely?" The catch shows an error state instead of pretending. Partial credit; the disable is now on my list.

The Thing That Clicked Today

Writing the tests for updateOpportunity before it existed forced a decision I would have skipped: what happens when the id is garbage. Code-first me would have written the happy path, shipped it, and met NaN in production. Test-first me had to decide up front -- because the third test would not let me not decide -- that a missing row throws P2025 and a non-numeric id gets rejected before Prisma ever sees it. Yesterday I said the tests remove the vagueness before the model sees the problem. Today I watched them remove the vagueness before I saw the problem.

The other click was quieter. CRUD is done -- the board creates, reads, updates, deletes, and everything after this is a bonus on top of a complete application. Two patterns for mutations now live side by side in the codebase, and I can articulate when each earns its keep: fetch-plus-route when something other than my own Next app needs to talk to the backend, Server Actions when a form inside the app mutates data. And the day ended with a README and six WHY-comments, which felt less like homework than like leaving supplies for the next person to walk into this codebase. The next person is me, Monday, mid-build-sprint. He is going to be grateful.
