DELETE, Built Twice

Exercise 3 / 6 . Level 1 + the optional Level 2 conversion . 45 min

Goal: a user can delete a listing, with a confirmation in front of it -- and since the lab offers an optional conversion to a Server Action afterward, I built it both ways on purpose. Same move as W6D4's two refresh strategies: do both, feel the difference, then decide with evidence instead of vibes.

Version 1 -- the API route and the button

// app/api/opportunities/[id]/route.js
export async function DELETE(request, { params }) {
  const { id } = await params;
  try {
    await prisma.opportunity.delete({ where: { id: parseInt(id) } });
    return NextResponse.json({ message: "Deleted" });
  } catch (error) {
    if (error.code === "P2025") {
      return NextResponse.json({ error: "Already gone" }, { status: 404 });
    }
    return NextResponse.json({ error: "Delete failed" }, { status: 500 });
  }
}
// app/opportunities/DeleteButton.js
"use client";
import { useRouter } from "next/navigation";

export default function DeleteButton({ id }) {
  const router = useRouter();

  async function handleDelete() {
    const confirmed = window.confirm(
      "Delete this listing? This cannot be undone.");
    if (!confirmed) return;

    const res = await fetch(`/api/opportunities/${id}`, { method: "DELETE" });
    if (res.ok) router.refresh();
  }

  return <button onClick={handleDelete} className="danger">Delete</button>;
}
The review checklist, honestly run

Does the handler actually delete from the database -- yes, verified in psql, the row count drops. Does the dialog fire BEFORE the request -- yes, and the early return on cancel means no request at all, which I confirmed in the network tab because a cancel that still fires is the bug this pattern exists to prevent. Does the list refresh -- yes, router.refresh() re-pulls the server component's data without a full reload, the same move as after CREATE. Cancel path: listing stays. Confirm path: listing gone from the page and from Postgres.

Why P2025 gets its own branch

Deleting a row that is already gone is not a server error, it is a stale page -- somebody else (or another tab) got there first. Prisma surfaces it as P2025, and mapping that to a 404 instead of a 500 means the client can tell "the thing you wanted is already done, refresh" apart from "something actually broke." Yesterday's test for the UPDATE action taught me this error code exists; today it earned a branch in production code.

Version 2 -- the conversion

// app/opportunities/actions.js -- second export
export async function deleteOpportunity(formData) {
  const id = parseInt(formData.get("id"));
  if (Number.isNaN(id)) throw new Error("Invalid opportunity id");

  await prisma.opportunity.delete({ where: { id } });
  revalidatePath("/opportunities");
}
// app/opportunities/DeleteForm.js -- small client island for the confirm
"use client";
import { deleteOpportunity } from "./actions.js";

export default function DeleteForm({ id }) {
  return (
    <form
      action={deleteOpportunity}
      onSubmit={(e) => {
        if (!confirm("Delete this listing? This cannot be undone."))
          e.preventDefault();
      }}
    >
      <input type="hidden" name="id" value={id} />
      <button type="submit" className="danger">Delete</button>
    </form>
  );
}

Tests came first here too -- two more in the suite, mirroring Exercise 1's shape: called once with the right where, and the NaN guard stops it at the door. The action itself is four lines of logic; the tests took longer than the implementation, and that ratio is fine, because the tests are the part that stays true while the implementation changes.

The confirm needed a client island anyway

The honest wrinkle in the "Server Actions need no client code" pitch: window.confirm is a browser API, so the confirm-then-maybe-preventDefault wrapper has to be a client component. The board stays a server component and renders this little island per card. So the real count: version 1 is a route file plus a client button with a fetch; version 2 is a server function plus a client form with no fetch. The conversion did not eliminate the client code -- the dialog is irreducibly client-side -- it eliminated the HTTP plumbing.

The comparison, and the decision

API route + buttonServer Action + form
piecesroute handler, fetch, router.refreshaction, form (refresh is revalidatePath, already inside)
serializationmine to write, both directionsFormData in, framework handles the rest
testable with yesterday's patternyes -- handler takes request/paramsyes -- action takes FormData, arguably simpler
callable from outside a Next appyes, it is just HTTPno -- forms in this app only
works before JS hydratesno -- onClick needs JSmostly -- the form posts natively, but so would the confirm-less delete

Kept: the Server Action, and the comment at the top of actions.js says why -- "Mutations from this app's own forms go through Server Actions; the API routes stay for anything that is not this app's forms." The DELETE route handler stays in the file too, deliberately, because Day 3 involves outside services and a plain HTTP surface has a way of becoming useful the moment something that is not a React form needs to talk to you.

Checkpoint

Both versions demoed against the full flow: cancel keeps, confirm deletes, board refreshes, Postgres agrees. Suite at nine green. One known wart carried forward to the checkpoint exercise: the delete button can be double-clicked, and the second confirm races the first delete. It loses politely thanks to the P2025 handling, but politely losing is not the same as not racing.
