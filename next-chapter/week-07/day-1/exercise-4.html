Test the GET Handler with Mocked Prisma

Exercise 4 / 4 . Level 2 . 35 min

Goal: write tests for the GET /api/opportunities handler from Week 6 -- the one that powers the board -- without touching the real database. Pure functions were the warm-up; this is the first test against code that talks to Postgres, and the whole technique is replacing Prisma with a fake so the test stays fast and deterministic. A real DB makes tests slow (network, query parsing) and flaky (rows change between runs). A mock makes them instant and identical every time.

The mock, hoisted above the imports

// app/api/opportunities/route.test.js
import { test, expect, vi, beforeEach } from "vitest";

// Tell Vitest: when anything imports @/lib/prisma, give it this fake.
// vi.mock is hoisted to the very top, so it runs before the imports below.
vi.mock("@/lib/prisma", () => ({
  prisma: { opportunity: { findMany: vi.fn() } },
}));

import { GET } from "./route.js";
import { prisma } from "@/lib/prisma";

beforeEach(() => {
  // wipe call history AND any mockResolvedValue setup between tests.
  // after this, findMany() returns undefined until a test sets it up.
  vi.clearAllMocks();
});
The hoist gotcha

Vitest physically lifts every vi.mock() call above all the imports before the file runs. That is why the factory -- the arrow function returning the fake -- cannot reference anything imported below it: at the moment the factory executes, those imports do not exist yet. If I wrote vi.mock("@/lib/prisma", () => ({ prisma: someImportedHelper })) I would get a confusing "cannot access before initialization." The fix today is to define the fake inline inside the factory, which I do. If I ever truly need to share a value between the factory and the test body, that is the job of vi.hoisted().

Three tests -- and set the fake return in every one

test("returns the opportunities the DB has", async () => {
  prisma.opportunity.findMany.mockResolvedValue([
    { id: 1, title: "Line cook", type: "job", createdAt: new Date("2026-06-01") },
  ]);

  const response = await GET();
  const data = await response.json();

  expect(data).toHaveLength(1);
  expect(data[0].title).toBe("Line cook");
});

test("returns an empty array when the DB is empty", async () => {
  prisma.opportunity.findMany.mockResolvedValue([]);

  const response = await GET();
  const data = await response.json();

  expect(data).toEqual([]);
});

test("orders opportunities newest first", async () => {
  // even though we ignore the return, the handler still calls findMany
  // and uses the result -- so it must be set or the handler throws.
  prisma.opportunity.findMany.mockResolvedValue([]);

  await GET();

  expect(prisma.opportunity.findMany).toHaveBeenCalledWith(
    expect.objectContaining({ orderBy: { createdAt: "desc" } })
  );
});
Why every test sets mockResolvedValue first

beforeEach(vi.clearAllMocks()) wipes the previous setup, so at the start of each test findMany returns undefined by default. If the handler runs against an unmocked findMany, the code that does opportunities.map(...) or even just hands the value to NextResponse.json chokes -- typically "cannot read properties of undefined." Even the ordering test, which does not care about the rows, has to set a value, because the handler still executes the whole body and uses the result. The rule is blunt: any test that triggers the handler sets the fake's return first.

What await response.json() is doing

Each test calls await GET() and gets back a NextResponse (which extends the web Response). To read the body as data I call await response.json(), which re-parses the JSON the handler serialized. So the round-trip is: handler does NextResponse.json(rows), the test does await response.json(), the test sees rows. If my Week 6 handler had returned a plain new Response(JSON.stringify(...)) instead, .json() still works the same way.

The third test is the interesting one

The first two assert on the body -- what comes out. The third asserts on the call -- that my handler asked Prisma for the rows in descending date order. That is a different kind of check: not "did I get the right answer" but "did I ask the question correctly." If someone later deletes the orderBy while refactoring, the board would silently start showing oldest-first and the body tests would still pass, because the fake returns whatever I tell it regardless of the args. Only the toHaveBeenCalledWith assertion catches that regression. When I first ran it, it was green -- the Week 6 handler does order desc -- so this one is a lock on existing, correct behavior.

Checkpoint

Three passing tests for the GET handler, Prisma fully faked, terminal green, and -- the thing I keep checking -- no real database was touched, which I can prove because the tests run in milliseconds with the dev server and the DB both off. I now have the exact pattern tomorrow needs: vi.mock the prisma module, set the fake per test, call the handler, assert on the body and on how Prisma was called. UPDATE and DELETE get tested the same way before I write them.

End of Day 1

Four cycles run: a setup-and-first-test, a pure function built entirely test-first, a feature the AI implemented from my tests and then helped me harden, and a handler tested against a faked database. The through-line is that my trust moved from the model's confidence to the suite's verdict -- and the suite is the part that scales when the AI is writing faster than I can read.
