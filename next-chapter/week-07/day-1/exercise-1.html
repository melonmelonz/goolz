Vitest Setup + First TDD Cycle

Exercise 1 / 4 . Level 1 . 30 min

Goal: get a test runner into the Week 6 app and run one complete red/green cycle on the smallest real function I can find. The function is getDomain(url) -- give it a URL, get back the host. It earns its place in my app because an Opportunity can carry an optional source link (the original job posting), and the card looks better showing "via indeed.com" than the full URL. Small, pure, perfect first test.

Install and wire the script

npm install --save-dev vitest
// package.json
"scripts": {
  "dev": "next dev",
  "build": "next build",
  "test": "vitest"
}
"vitest" not "vitest run"

Plain vitest is watch mode: it stays alive and re-runs the moment I save. That is the whole point during development -- I want to see red turn green in real time as I type, not run a command, read output, edit, run again. vitest run runs once and exits; that is for CI, where nothing is sitting at the terminal watching. I will add a separate test:ci for that later in the week.

RED -- write the failing test first

// src/utils/getDomain.test.js
import { test, expect } from "vitest";
import { getDomain } from "./getDomain.js";

test("extracts domain from a URL", () => {
  expect(getDomain("https://www.indeed.com/jobs?q=forklift")).toBe("www.indeed.com");
});

Save, then in a second terminal: npm test. It fails immediately -- and not on the assertion. The import itself throws, because getDomain.js does not exist yet. That is the failure I wanted. RED. The test is making a claim about a function that has no implementation, which is the entire premise of test-first: the spec exists before the code.

GREEN -- the minimum that passes

// src/utils/getDomain.js
export function getDomain(url) {
  return new URL(url).hostname;
}

Save. Watch mode re-runs on its own and the check goes green. One line. I did not reach for a regex or string-splitting on slashes -- the platform already has a URL parser that knows what a hostname is, and reaching past it would be me reimplementing a solved problem and inventing new bugs. The minimum that passes is the right amount of code.

RED again -- an edge case as a second test

test("preserves the www subdomain", () => {
  expect(getDomain("http://www.linkedin.com/jobs/view/123")).toBe("www.linkedin.com");
});

Run again -- and it already passes. The URL parser keeps the www as part of the hostname, which is exactly what I want on the card; I am not in the business of stripping subdomains. Sometimes a test you write to drive new behavior turns out to already be green, and that is fine -- it is not wasted. I now own a regression test that locks in "www stays," so if some future-me decides to "clean up" domains and accidentally strips it, this test catches it.

A test that passes on the first run still earns its keep

The instinct is "if it passed without changing code, the test did nothing." Wrong job. A green-on-arrival test is not driving new behavior, it is pinning existing behavior so it cannot drift. The www case documents a decision -- "we show the subdomain" -- in executable form. Six months from now nobody has to remember that decision; the test remembers it and fails loudly if anyone reverses it by accident.

Refactor step -- ask the AI what I am missing

The function is green and tiny, which is the right moment to ask the model for the edge cases I have not thought of. Prompt: "Here is my getDomain and its two tests. What edge cases am I missing, real-world first, paranoid last?"

It came back with: a bare hostname like "localhost:3000" with no protocol (throws, because new URL needs a scheme); a port that should probably be dropped for display; mailto: and other non-http schemes; and malformed input like an empty string or null. Keep/reject/modify: the empty/null case is real -- the source link is optional, so an absent value will reach this function, and right now getDomain(null) throws. That one becomes a test. The port and the protocol-less host are paranoid for my use -- the links I store come from a controlled create form that requires a full https:// URL -- so I reject those for now. I will not add a test for a case that cannot occur in my app. 

test("returns empty string for a missing source link", () => {
  expect(getDomain("")).toBe("");
  expect(getDomain(null)).toBe("");
});
// getDomain.js -- guard the real case, nothing more
export function getDomain(url) {
  if (!url) return "";
  try {
    return new URL(url).hostname;
  } catch {
    return "";
  }
}

Back to green, now with the one guard that maps to a real input and not a single line for the paranoid cases. That is the discipline the edge-case review is supposed to teach: the AI is good at generating the whole list, and I am the one who decides which items are load-bearing for this app.

Checkpoint

Vitest is installed and watching. Three passing tests, one of which guards a real edge case I would have shipped past. I ran a complete cycle -- red because the function did not exist, green on the minimum, a second red-then-green for an edge case, and a refactor pass guided by the model but gated by me. The terminal is green and I am ready to demo it.
