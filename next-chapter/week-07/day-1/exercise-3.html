TDD with an AI Pair + Edge-Case Discovery

Exercise 3 / 4 . Level 2 . 55 min

Goal: build one real feature for the Opportunities board by writing the tests first, handing them to the AI to implement, then turning around and asking the AI what I missed. This is Pattern 2 (I write the test, AI writes the code) bolted to Pattern 3 (AI suggests edge cases) -- the combination I expect to actually live in. The feature is filterByType(opportunities, type): narrow the board to just jobs, just certifications, or just services. It pairs with the type field I added in Week 6 and the type chips on the board.

Step 1 -- the cases as English bullets

Before any code, the spec as plain bullets so I know what I am asking the AI to satisfy:

  • empty input array returns an empty array
  • returns only the items whose type matches
  • returns an empty array when nothing matches
  • matching is case-insensitive ("Job" matches "job")
  • a falsy / "all" type returns everything unfiltered (the board's default)

Step 2 -- RED, the bullets as failing tests

// src/utils/filterByType.test.js
import { test, expect } from "vitest";
import { filterByType } from "./filterByType.js";

const rows = [
  { id: 1, title: "Forklift cert", type: "certification" },
  { id: 2, title: "Line cook",     type: "job" },
  { id: 3, title: "Resume help",   type: "service" },
  { id: 4, title: "Warehouse",     type: "job" },
];

test("empty input returns empty", () => {
  expect(filterByType([], "job")).toEqual([]);
});
test("returns only matching items", () => {
  expect(filterByType(rows, "job").map((r) => r.id)).toEqual([2, 4]);
});
test("returns empty when nothing matches", () => {
  expect(filterByType(rows, "internship")).toEqual([]);
});
test("matching is case-insensitive", () => {
  expect(filterByType(rows, "JOB").map((r) => r.id)).toEqual([2, 4]);
});
test("a falsy type returns everything", () => {
  expect(filterByType(rows, "")).toEqual(rows);
});

Run: five reds on the missing import. Now I have a spec precise enough to hand off.

Step 3 -- Pattern 2: hand the failing tests to the AI

The prompt, with the test file pasted under it:

Prompt

"Here are my failing Vitest tests for filterByType. Write the function that makes them pass. Do not add features beyond what the tests describe."

What it returned, essentially first-try:

// src/utils/filterByType.js
export function filterByType(opportunities, type) {
  if (!type) return opportunities;
  const wanted = type.toLowerCase();
  return opportunities.filter((o) => o.type.toLowerCase() === wanted);
}

Saved it, watch mode re-ran, five green. No iteration needed -- and that is the point of Pattern 2, not luck. There was nothing for the model to guess. The empty-input case falls out of filter for free, the case-insensitivity is the two toLowerCase() calls the third and fourth tests demanded, and the "falsy returns all" line is exactly the fifth test made executable. The tests did the specifying; the AI did the typing.

"Do not add features beyond what the tests describe"

That sentence in the prompt earns its place. Left unconstrained, the model likes to be helpful -- it will add a second parameter for sorting, or a fuzzy match, or a null-guard I did not ask for, and now I am reviewing code that does more than my spec and my tests do not cover the extra. Telling it to satisfy the tests and stop keeps the implementation exactly as wide as the spec. If I want more behavior, I write more tests first. The tests are the contract; the prompt just enforces it.

Step 4 -- Pattern 3: ask what I missed

Prompt

"Here is my filterByType and its tests. What edge cases am I missing? List them in priority order -- real-world risks first, paranoid edge cases last."

The list it produced, and my keep/reject/modify on each:

SuggestionReal or paranoidVerdict
an item with a missing/undefined type fieldreal -- legacy rows predate the type columnKEEP, write a test
opportunities itself is null/undefinedreal -- a failed fetch can pass undefined downKEEP, write a test
whitespace in the type, e.g. " job "paranoid -- type comes from a fixed select, never typedREJECT
duplicate items in the arrayparanoid -- not filter's job; it returns what it is givenREJECT
a 100,000-item boardparanoid -- a personal reentry board, dozens of rowsREJECT

Two reals. Both are about garbage arriving from elsewhere in the system, which is exactly the kind of thing the function should survive without throwing. Back to RED with two new tests, then patch the implementation to pass them -- and nothing more. 

test("skips items with a missing type", () => {
  const mixed = [...rows, { id: 5, title: "Old row" }]; // no type
  expect(filterByType(mixed, "job").map((r) => r.id)).toEqual([2, 4]);
});
test("a null list returns empty, does not throw", () => {
  expect(filterByType(null, "job")).toEqual([]);
});
export function filterByType(opportunities, type) {
  if (!opportunities) return [];          // null list -> empty
  if (!type) return opportunities;
  const wanted = type.toLowerCase();
  return opportunities.filter((o) => o.type?.toLowerCase() === wanted);
}

The ?. on o.type makes a missing type short-circuit to undefined, which never equals wanted, so that row drops out instead of crashing the .toLowerCase(). The leading null-guard handles the failed-fetch case. Seven green. I added exactly the two guards that map to things that happen in my system and not one line for the three that do not.

Reflection: what the AI surfaced

The two cases I had genuinely missed were both "bad data from upstream" -- the legacy row with no type, and the undefined array from a broken fetch. Left to myself I would have tested the happy paths and shipped, and the undefined-array one would have been a real production crash the first time a fetch failed. The three I rejected were the model being thorough past the point of usefulness -- whitespace, dedup, and scale all matter in some app, just not in a personal board fed by a fixed select. Writing the tests first did change what I built: the case-insensitivity and the "falsy returns all" default were both decisions I made while writing assertions, before the AI ever saw the problem, and they came out clean because the spec was settled first.

Checkpoint

A working filter the AI implemented from my tests on the first pass, plus two edge-case tests I added after its review and kept because they map to real inputs. Seven green, and -- more to the point -- a documented trail of what I kept, what I rejected, and why, which is exactly the "what did the AI write vs. what did I decide" record the Phase 2 gate wants.
