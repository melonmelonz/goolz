Day 1 -- TDD + AI

NCD . WK7 . D1 . four exercises loaded . the AI stops being trusted and starts being verified

Six weeks of building with an AI pair. I have watched it generate code, kept some of it, thrown some of it out, rewritten plenty of it by hand. The loop the whole time has been the same and I have known it was thin: I describe what I want, the model writes something confident, I read it, maybe I run it, and I hope. Today that loop gets a backbone. The move is to write the test first -- before the code exists -- watch it fail, then have the AI write code that makes it pass. The test is the spec, the spec is the prompt, and the passing test is the proof the model did the thing I asked instead of a thing that merely looks like it.

The reason this is more than a tidy habit is the inversion. Without tests, the AI's confidence is the only signal I have, and its confidence is not always earned -- it will hand me an isEven that breaks on a negative zero and never blink. With a test in front of it, there is nothing to be confident about; there is a bar, and the code clears it or it does not. Tests plus AI is strictly stronger than either alone, because the AI is genuinely excellent at two things -- turning a precise spec into an implementation, and answering "what edge cases am I missing" -- and a test suite is exactly the structure that puts both of those to work and then checks the result. The instinct that says "the AI writes the code so I need fewer tests" is backwards. It writes code faster than I can read it line by line. Tests are the only way to keep up.

Nothing here undoes Week 6. My ReEntry Tech app stays exactly where it left off Friday -- the Opportunities board reads, the form creates, Postgres holds it. Today I bolt Vitest on top, a fast modern runner that watches my files and flips red to green as I type, and I get reps on the cycle before it matters. Tomorrow, when I add UPDATE and DELETE, I write the failing tests first and let the AI implement against them. So today's stakes are deliberately small: a couple of pure functions, one feature built test-first with an AI pair, and one handler tested with Prisma faked out. The point is the discipline, not the difficulty.

That sentence is already a test -- two of them. I have been doing this informally for years; today is just the syntax that makes it executable, and the runner that holds me to it.

Lecture Notes -- The Cycle Is Three Words
PhaseWhat happensState
Redwrite a test for behavior that does not exist; run it; watch it failfailing
Greenwrite the minimum code to pass; run it; watch it passpassing
Refactorclean up the code; re-run; it still passesstill passing

The crucial bit is order. The test comes first, which forces me to state the spec before I write a line of implementation. And a single test is doing three jobs at once: it is the spec (a precise description of intended behavior), the documentation (future-me reads it to remember what the code is for), and the regression net (if anyone breaks this in six months, it screams).

Lecture Notes -- Vitest, And Watch Mode
npm install --save-dev vitest

// package.json
"scripts": {
  "test": "vitest"      // watch mode -- NOT "vitest run"
}

Test files live next to the code they test: src/utils/getDomain.js gets src/utils/getDomain.test.js. Vitest auto-discovers anything matching *.test.{js,ts,jsx,tsx} -- no central tests/ folder. Plain vitest stays running and re-runs on every save, so I literally watch red become green. vitest run runs once and exits, which is for CI, not for sitting next to my editor. The watch UI takes single keystrokes: a all, f failed only, p filter by path, t filter by test title, q quit.

Lecture Notes -- The Three TDD-with-AI Patterns

All three combine tests and the model. All three end with keep / reject / modify on whatever it produces.

Pattern 1 -- AI writes the test, I write the code. For when I know the behavior but not the runner's syntax. "Write me 5 Vitest cases for a function that formats a date as X ago." Useful when test syntax is the friction.

Pattern 2 -- I write the test, AI writes the code. Pure TDD, and the strongest of the three. I hand it the failing tests as the prompt: "here are my failing tests, write the function that makes them pass, no extra features." The tests are the spec; there is nothing to misinterpret. This is the one I will lean on most.

Pattern 3 -- AI suggests edge cases. I wrote the function and some tests; now I want to know what I missed. "Here is my function and my tests -- what edge cases am I missing, real-world risks first, paranoid last." It is excellent at "have you considered." Some suggestions are real, some are paranoid; keep/reject/modify hard, only add the ones that matter for this app.

Lecture Notes -- Mocking Prisma

Tests should be fast and deterministic. A real database is neither -- it is slow and its rows change between runs, so a passing test today flakes tomorrow. The fix is to swap Prisma for a fake during tests.

import { test, expect, vi } from "vitest";

// hoisted to the very top -- runs before any import below
vi.mock("@/lib/prisma", () => ({
  prisma: { opportunity: { findMany: vi.fn() } },
}));

import { GET } from "./route.js";
import { prisma } from "@/lib/prisma";

prisma.opportunity.findMany.mockResolvedValue([ /* fake rows */ ]);

The gotcha is the hoist. Vitest lifts every vi.mock() above the imports, so the factory cannot reference an imported variable -- it does not exist yet when the factory runs. Define the fake inline inside the factory (which I do above) and it is fine; if I genuinely need to share data, that is what vi.hoisted() is for. Then in each test I set what the fake returns, call the handler, and assert -- no database touched.

Lecture Notes -- Failure Modes Tests Catch
FailureCaught by
works on the example, dies on the edge (NaN, negative zero, empty string)edge-case tests with weird inputs
refactor silently changes existing behaviorold tests still passing -- the regression net
off-by-one: returns 11 when I asked for 10a test asserting the exact count
hallucinated method (array.shuffleInPlace())the test fails in seconds, on the spot

Every one of these is invisible without tests and obvious within seconds with them. That is the whole trade.

Verbal Mini-Demo -- Walk One Cycle Out Loud

Partner had me trace one full cycle pointing at the screen. I picked formatOpportunityAge from Exercise 2. The failing test first: expect(formatOpportunityAge(fiveMinAgo, NOW)).toBe("5 minutes ago") -- read it aloud, it specifies the minutes branch and nothing else. Then RED, because the function did not exist. Then the implementation, a chain of thresholds floor-dividing seconds into the right bucket. Then GREEN in the terminal, watch mode flipping the moment I saved. The thing I had to articulate is why now is a parameter and not new Date() inside the function: because a function that reads the real clock is non-deterministic, and a non-deterministic function cannot be tested -- the same input gives a different answer every second.

Their follow-up was the good one: "what would you have done if the AI's first attempt failed two of your tests?" Read which two. A failure is information -- it tells me exactly which branch the model got wrong, in its own words via the diff. Then I decide per failure whether the test is wrong or the code is wrong, and most of the time with a precise spec it is the code, so I hand the two failing cases back and say "these two are red, the rest are green, fix only these." That is the loop, and it is faster than reading a 40-line function line by line trying to spot the bug by eye.

The Thing That Clicked Today

I came in thinking tests-first would feel slower, and for the first twenty minutes it did -- writing a test for a function that does not exist feels like building scaffolding for a building you have not drawn. Then it flipped, and the place it flipped was Exercise 3. I wrote five tests for filterByType, handed them to the AI, and got back a correct implementation on the first try -- because there was nothing for it to guess. Every prototype I have ever built went wonky exactly at the spots where I had been vague, and the test had quietly removed all the vagueness before the model ever saw the problem. The tests were not overhead on top of the prompt. They were the prompt, in the only language that cannot be misread.

The deeper shift is about where my trust lives. For six weeks my trust lived in the model's confidence -- I read the code, it looked right, I moved on, and the bugs I shipped were the ones that looked right. Today my trust moved out of the model and into the suite. I do not have to believe the AI got filterByType right; I can watch four green checks and one red one and know precisely. For ReEntry Tech that is not academic. The data is about people's actual reentry -- jobs and certifications they will act on -- and "it looked right when I read it" is not a standard I want that data held to. The test is the standard. The AI is fast, and the suite is the part that keeps it honest while it goes fast.
