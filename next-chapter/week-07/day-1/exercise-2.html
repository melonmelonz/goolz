TDD a Pure Function

Exercise 2 / 4 . Level 1 . 30 min

Goal: build formatOpportunityAge(date, now) with zero implementation written until the tests exist. It turns a timestamp into a human string -- "just now", "5 minutes ago", "2 days ago" -- for the byline under each Opportunity card, so a jobseeker can see at a glance how fresh a posting is. A pure function with a fiddly set of branches is the ideal TDD substrate: easy to test, easy to get an off-by-one wrong, and worth pinning down precisely.

The spec, as a table

A test is only as good as the spec it encodes, so I write the rule down first. Every test maps to exactly one row.

Age of date relative to nowOutput
0 -- 59 secondsjust now
1 -- 59 minutesX minutes ago
1 -- 23 hoursX hours ago
1 -- 29 daysX days ago
30 days up to (not incl.) 365X months ago, X = floor(days / 30)
365 days or moreX years ago, X = floor(days / 365)

Deliberately simple math -- 30-day months, 365-day years, integer floor. Real date libraries are smarter about calendars; today is about TDD discipline, not leap years. The weird-reading "1 months ago" is on purpose: one format string for the whole months row keeps the branch logic clean. Correct pluralization is a refactor-step improvement -- I write a test for it, then change the code -- not something I smuggle in now.

RED -- the tests, all failing, one per row

// src/utils/formatOpportunityAge.test.js
import { test, expect } from "vitest";
import { formatOpportunityAge } from "./formatOpportunityAge.js";

const NOW = new Date("2026-06-08T12:00:00Z");
const ago = (ms) => new Date(NOW.getTime() - ms);
const SEC = 1000, MIN = 60 * SEC, HOUR = 60 * MIN, DAY = 24 * HOUR;

test('"just now" under a minute', () => {
  expect(formatOpportunityAge(ago(30 * SEC), NOW)).toBe("just now");
});
test('"5 minutes ago"', () => {
  expect(formatOpportunityAge(ago(5 * MIN), NOW)).toBe("5 minutes ago");
});
test('"3 hours ago"', () => {
  expect(formatOpportunityAge(ago(3 * HOUR), NOW)).toBe("3 hours ago");
});
test('"2 days ago"', () => {
  expect(formatOpportunityAge(ago(2 * DAY), NOW)).toBe("2 days ago");
});
test('"1 months ago" at 35 days (floor(35/30))', () => {
  expect(formatOpportunityAge(ago(35 * DAY), NOW)).toBe("1 months ago");
});
Why "now" is a parameter

The function never calls new Date() inside itself -- the caller passes now. A function that reads the real clock is non-deterministic: the same date produces a different string every second, so there is no stable value to assert against and the test is impossible to write. By injecting now, the function becomes pure -- same two inputs, same output, forever -- and the test pins an exact answer. In the real card I will call formatOpportunityAge(opp.createdAt, new Date()); the clock-reading stays at the edge, where the impurity belongs, and the core stays testable.

Run it: five failures, all on the missing import. RED.

GREEN -- implement to the spec

// src/utils/formatOpportunityAge.js
export function formatOpportunityAge(date, now) {
  const seconds = Math.floor((now - date) / 1000);
  const minutes = Math.floor(seconds / 60);
  const hours = Math.floor(minutes / 60);
  const days = Math.floor(hours / 24);

  if (seconds < 60) return "just now";
  if (minutes < 60) return `${minutes} minutes ago`;
  if (hours < 24) return `${hours} hours ago`;
  if (days < 30) return `${days} days ago`;
  if (days < 365) return `${Math.floor(days / 30)} months ago`;
  return `${Math.floor(days / 365)} years ago`;
}

Each if is one row of the table, in order, narrowest first. The ordering is load-bearing: by the time control reaches the months line I already know it is at least 30 days, so I only need the upper bound. Save, and all five flip green as watch mode re-runs.

The edge case: a date in the future

The spec table starts at zero and goes up. It says nothing about a date after now -- which can happen: a clock skew between the server and the browser, or a scheduled posting dated for tomorrow. Decide first, then test. My decision: a future date reads "just now" rather than a negative-number absurdity like "-5 minutes ago", because the byline is a freshness hint and "this is brand new" is the least wrong thing to say. 

test("a future date reads 'just now', not a negative", () => {
  const future = new Date(NOW.getTime() + 5 * MIN);
  expect(formatOpportunityAge(future, NOW)).toBe("just now");
});

RED -- with negative seconds, seconds < 60 is true, so it already returns "just now" by accident. It passes. But "passes by accident" is fragile; I make the intent explicit so a future refactor cannot break it silently: 

const seconds = Math.floor((now - date) / 1000);
if (seconds < 60) return "just now";   // covers future dates too: negative < 60

It was already correct; the test now documents that it is correct on purpose. Green.

Reflection: slower or faster?

Tests-first felt slower for the first two tests and faster by the fifth. Writing assertions for a function that does not exist is friction up front -- but by the time I wrote the implementation I had already made every decision (the boundaries, the floor, the future case), so the code came out in one pass with nothing to debug. The slowness was front-loaded thinking I would have done anyway, just usually after the bug instead of before it.

Checkpoint

Six passing tests, written before a line of formatOpportunityAge existed. The spec table became the test suite became the implementation, in that order, and the function dropped out almost mechanically once the spec was pinned. That is the feeling the exercise is selling: when the spec is precise enough, the code is the easy part.
