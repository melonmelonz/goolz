RAG Worked Example

Exercise 2 / 4 . Level 1-3 . 30 min

The course provided a starter script, rag.mjs. My job was to run it over a real set of documents and understand what it actually does at each step -- not just "it worked" but why the retrieval finds different chunks for different questions, what the system-prompt guard does, and where the chunk size matters. I used three markdown files representing a realistic reentry resource list: housing, legal aid, and jobs. Anonymous -- no real organization names, no real addresses.

The Script: rag.mjs

// rag.mjs -- retrieval-augmented generation over a local resource folder
// models: text-embedding-3-small (retrieval), gpt-5-mini (chat)

import fs from "fs";
import path from "path";
import OpenAI from "openai";
import { fileURLToPath } from "url";

const client = new OpenAI(); // reads OPENAI_API_KEY from env
const EMBED_MODEL = "text-embedding-3-small";
const CHAT_MODEL  = "gpt-5-mini";
const TOP_N       = 2;
const RESOURCES_DIR = path.join(
  path.dirname(fileURLToPath(import.meta.url)),
  "resources"
);

// --- STEP 1: CHUNK
// Split each .md file on blank lines -> one chunk per paragraph.
// A blank line is the natural boundary between resource entries.
function chunkFile(filePath) {
  const text = fs.readFileSync(filePath, "utf8");
  return text
    .split(/\n\n+/)
    .map(s => s.trim())
    .filter(s => s.length > 20); // drop near-empty paragraphs
}

function loadAllChunks(dir) {
  const files = fs.readdirSync(dir).filter(f => f.endsWith(".md"));
  const chunks = [];
  for (const f of files) {
    const pieces = chunkFile(path.join(dir, f));
    for (const text of pieces) chunks.push({ text, source: f });
  }
  return chunks;
}

// --- STEP 2: EMBED
async function embedTexts(texts) {
  const resp = await client.embeddings.create({
    model: EMBED_MODEL,
    input: texts,
  });
  // resp.data is sorted by index
  return resp.data.map(d => d.embedding);
}

// --- STEP 3: RETRIEVE (cosine similarity)
function cosine(a, b) {
  let dot = 0, magA = 0, magB = 0;
  for (let i = 0; i < a.length; i++) {
    dot  += a[i] * b[i];
    magA += a[i] * a[i];
    magB += b[i] * b[i];
  }
  return dot / (Math.sqrt(magA) * Math.sqrt(magB));
}

function topN(queryVec, chunkVecs, chunks, n) {
  const scored = chunks.map((c, i) => ({
    chunk: c,
    score: cosine(queryVec, chunkVecs[i]),
  }));
  scored.sort((a, b) => b.score - a.score);
  return scored.slice(0, n);
}

// --- STEP 4: INJECT + ANSWER
async function rag(query) {
  const chunks    = loadAllChunks(RESOURCES_DIR);
  const texts     = chunks.map(c => c.text);
  const allVecs   = await embedTexts(texts);
  const [qVec]    = await embedTexts([query]);
  const results   = topN(qVec, allVecs, chunks, TOP_N);

  const context = results
    .map(r => `[${r.chunk.source}]\n${r.chunk.text}`)
    .join("\n\n---\n\n");

  const messages = [
    {
      role: "system",
      content:
        "You are a resource assistant for a reentry program. " +
        "Answer ONLY from the context provided below. " +
        "If the answer is not in the context, say exactly: " +
        "'I don't have that information.' Do not guess.\n\n" +
        "CONTEXT:\n" + context,
    },
    { role: "user", content: query },
  ];

  const resp = await client.chat.completions.create({
    model: CHAT_MODEL,
    messages,
    max_tokens: 300,
  });

  console.log("\nQuery:", query);
  console.log("\nTop chunks retrieved:");
  results.forEach(r =>
    console.log(`  [${r.chunk.source}] score=${r.score.toFixed(4)}: "${r.chunk.text.slice(0, 80)}..."`)
  );
  console.log("\nAnswer:", resp.choices[0].message.content.trim());
}

const query = process.argv[2];
if (!query) {
  console.error("Usage: node rag.mjs \"your question here\"");
  process.exit(1);
}

rag(query).catch(err => { console.error(err); process.exit(1); });

What I noticed as someone who has read the embeddings code before

Three things stood out. First, the retrieval picks different chunks for different questions -- that is the whole point, and it is satisfying to watch it work. The cosine scores for the first two queries are in the 0.86-0.89 range, which is strong semantic alignment. The scores for the refund query are 0.32 and 0.30, which are weak -- the model found the least-bad chunks but they are clearly not answers. The system-prompt guard does the rest.

Second, the out-of-context refusal is not magic. It works because the system prompt says "answer ONLY from the context provided" and "if the answer is not in the context, say exactly: I don't have that information." The model follows that instruction. If I removed the guard, it would hallucinate a plausible-sounding refund policy. The guard is a design choice, not a default.

Third, text-embedding-3-small produces 1536-dimensional vectors. The cosine similarity I wrote is doing real linear algebra over those 1536 numbers for every chunk, every query. For three files and maybe fifteen chunks that is fast -- under a second. At ten thousand chunks it would start to matter, which is the real argument for vector databases like Pinecone or pgvector. For this exercise, a flat in-memory array is fine and it makes the math visible.

The retrieval found the new file without any changes to the script

This is the point of the pattern. I dropped a new markdown file in the folder and re-ran. The script reads the directory at runtime, chunks everything it finds, embeds it, and the new chunks compete on the same similarity measure as the old ones. Adding knowledge to the system is editing a text file. The model does not change. The workflow does not change. The only thing that changes is the documents in the folder. That is the upsell for First 90: "AI that knows the program's actual resource list" means Renee edits a markdown file when a new employer starts hiring or a clinic changes its hours, and the AI immediately knows the update. No retraining. No fine-tuning. A text editor and a file save.

Level 3: Chunking Comparison -- Paragraph vs Sentence

I rewrote the chunk function to split by sentence instead of paragraph -- splitting on period-space rather than blank lines -- and re-ran the expungement query. 

// sentence-level chunking (Level 3 comparison)
function chunkFileBySentence(filePath) {
  const text = fs.readFileSync(filePath, "utf8");
  return text
    .split(/(?<=[.!?])\s+/)
    .map(s => s.trim())
    .filter(s => s.length > 20);
}

Paragraph chunks win for resource documents

With sentence chunking, the first retrieved chunk was "Walk-in hours are 10am to 2pm, no appointment needed." No organization. No location. No day of the week. The sentence that named the legal-aid clinic and specified the first Tuesday of each month was in a different chunk, which scored lower and did not make the top 2. The answer was accurate for the information it had, and completely useless in practice.

The lesson is that a chunk is the unit of context retrieval. If an entry in your resource list is naturally "one thing" -- a name, a day, hours, an address, a note -- splitting it across multiple chunks severs the connections that make it actionable. The embedding for "10am to 2pm" does not know it belongs to the legal-aid clinic two sentences earlier. Paragraph-level chunking keeps each entry whole. For this kind of document -- short, self-contained resource entries, one per paragraph -- it is the right call without question.

For a different kind of document -- a 50-page policy manual where each section covers one topic -- you would choose differently, probably splitting on section headers rather than paragraphs. The chunking strategy is a design decision that depends on the structure of the documents. There is no universal answer, which is why running the comparison yourself matters.
