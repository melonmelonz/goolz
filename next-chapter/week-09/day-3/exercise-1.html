Extend Your Workflow

Exercise 1 / 4 . Level 1-3 . 40 min

First 90 runs. The happy path works: an intake note comes in over the webhook, the AI step extracts a JSON object, the row lands in the sheet, Twilio fires an SMS for urgent appointments. What I proved yesterday is that the thing can work. Today's job is making it work reliably when the input is bad, the AI is creative, or nobody is watching. A Zap that silently skips a court-date appointment is not a working Zap. It is a liability.

The Final Workflow Shape

  [1] TRIGGER: Catch Hook (Webhook)
         |
         v
  [2] AI: Extract JSON
         { name, type, nextDate, urgency, isReal }
         |
         v
  [3] FILTER (guard): continue ONLY if
         type IN [appointment, court, housing, employment, other]
         AND nextDate is not empty
         |-- FAILS? --> [3b] Email-by-Zapier: raw payload
         |                  + AI output to penn@...
         v
  [4] FORMATTER: Date/Time -> Convert Format
         input: {{2.nextDate}}  (free text from AI)
         output: YYYY-MM-DD
         |
         v
  [5] AI: Draft Reminder Text
         "Write a one-sentence reminder for a resident
          named {{2.name}} about their {{2.type}} on
          {{4.output}}. Keep it under 25 words. Plain text."
         |
         v
  [6] PATHS:
         |--[A] urgency=high OR type=court
         |       [6A-1] Slack: DM on-call case manager
         |       [6A-2] Twilio SMS: to on-call number
         |
         |--[B] urgency=normal AND type != court
         |       [6B-1] Google Sheets: append row
         |                (name, type, date, reminder text)
         |       [6B-2] queue for Monday digest
         |
         |--[C] nextDate missing or type unrecognized
                 [6C-1] Google Sheets: append to review queue tab

Part A -- The Filter Guard and Failure Notification

The Filter goes right after the AI step. The conditions are specific: type must be a member of the allowed set (appointment, court, housing, employment, other) and nextDate must exist and be non-empty. If either condition fails, the Zap stops -- but not silently.

I added a separate Email-by-Zapier step on the failure branch. It sends the raw webhook payload and the full AI output to my email, with a subject line of "First 90 filter blocked -- review." That gives me two things: a record of everything the filter ever blocked, and the data I need to understand whether the AI prompt needs tuning. Failures are information. The filter does not hide them, it surfaces them.

Tested: passing and failing inputs both confirmed in Zap History

I sent a well-formed test webhook -- real name, type "court," a date string, urgency "high" -- and confirmed the Zap continued through all six steps. Then I sent a deliberately bad one: type "unknown," nextDate empty. The Filter blocked it at step 3, the fallback email fired with the raw payload, and Zap History showed a clean "Stopped by Filter" entry. Visible failure is the goal. I got visible failure.

Part B -- Paths: Three Routes, Three Different Outcomes

The Paths step at step 6 has three branches. The logic is readable:

PathConditionActions
A -- Urgenturgency = high OR type = courtSlack DM to on-call case manager + Twilio SMS to on-call number immediately
B -- Normalurgency = normal AND type != courtGoogle Sheets append (name, type, date, reminder text) + tag for Monday digest
C -- Reviewanything that passed the Filter but has a missing or garbled date after Formatterappend to a separate "Review Queue" tab in the sheet for the case manager to handle manually

Path C deserves a note. The Filter already blocks empty nextDate values, so Path C is for the case where the AI returned something non-empty that the Formatter step cannot parse into a date -- "sometime next week," or a string in a format the date converter cannot handle. Those get logged to the review tab instead of being quietly dropped. Renee can look at that tab on Monday and handle the two or three rows that needed a human eye.

Part C -- Date Normalizer and Reminder Drafter

The Formatter by Zapier step (step 4) uses the "Date / Time" action, "Convert Format," with the input set to {{2.nextDate}} -- whatever the AI returned -- and the output format set to YYYY-MM-DD. Zapier's Formatter handles a surprisingly wide range of input formats: "June 14th," "6/14/26," "next Tuesday" relative to the run date. It does not handle everything, which is exactly what Path C is for.

The second AI step (step 5) gets the normalized date and drafts the one-line reminder the resident will actually receive. The prompt is brief and constrained: 

System: You write short, warm, plain-text appointment reminders.
        No markdown. No quotes. Maximum 25 words.

User: Write a reminder for a resident named {{2.name}} about
      their {{2.type}} appointment on {{4.output}}.
Why a second AI step instead of doing this in the first one

The first AI step has one job: parse intake text into structured fields. Asking it to also draft a reminder in the same output is asking it to produce two different formats at once -- JSON for the router and plain text for the resident. That is a prompt that fights itself. Splitting into two steps keeps each step's instruction simple and its output predictable. The cost is one extra API call per run. On this volume -- maybe thirty residents, a handful of intakes a day -- that is cents a month. The reliability is worth it.

Deliverable

A six-step Zapier workflow with: a Filter guard (step 3) that passes only valid, date-bearing records; a failure-notification fallback email for everything the filter blocks; a Formatter step (step 4) that normalizes the AI's free-text date to YYYY-MM-DD; a second AI step (step 5) that drafts the resident's reminder text; and a three-branch Paths step (step 6) routing urgent records to immediate SMS/Slack, normal records to the sheet and digest queue, and garbled-date records to the review tab. Both passing and failing test runs confirmed in Zap History.
