Day 2 -- Automation Day 1: Zapier + AI Workflows

NCD . WK9 . D2 . five exercises loaded . the day I built something a case manager can edit at 9pm without me

Yesterday I mapped a business problem: a small reentry nonprofit where two case managers hand-text appointment reminders every evening because there is no system. Thirty residents, parole check-ins, court dates, forklift certs -- all of it living in somebody's head and a spreadsheet that does not talk to a phone. I named it "First 90," because the first ninety days out is where most of the critical dates cluster. Yesterday was the map. Today I build it.

The build tool is Zapier. I want to be honest about how that landed for me, because I think the discomfort is actually the lesson. I have written kernel modules in Rust. I process LiDAR point clouds. Handing me Zapier's field-picker UI instead of a text editor feels like being asked to assemble furniture with oven mitts on. The reflex to just write the thing in Node -- 40 lines, done, deployed to a Worker in ten minutes -- is loud. I notice it every time I click a dropdown where I would normally type a function name. That tension is real, and I am not going to pretend it is not there. But the reason I am learning to work around the reflex is that the client is not me, and the thing I build has to survive after I leave.

The part that makes a $50 gig a $500 gig is putting AI in the middle. A webhook fires, a free-text intake note arrives, and instead of the case manager parsing it by hand, a gpt-5-mini call extracts a clean structured record: who, what kind of appointment, when, how urgent. The AI step turns unstructured human language into something a Filter can act on and a spreadsheet can accept. That is the value -- not the routing, not the logging, the AI-in-the-middle that makes the rest possible. Without that step you are just forwarding emails. With it you are running a triage system.

Lecture Notes -- Trigger / Action / Result

The fundamental unit of Zapier is a Zap, and every Zap follows one pattern: something happens (the trigger), Zapier does something about it (one or more actions), and the result lands somewhere useful. The trigger is always an event in some app -- a new email, a form submission, a webhook POST, a calendar event. The actions are what Zapier does in response -- create a row, send a message, call an API, run an AI prompt. The result is what the human on the other end sees: a Slack message, a spreadsheet row, an email, a logged record.

The course represents it as a linear flow and I think the ASCII version makes it concrete:

TRIGGER                ACTION 1              ACTION 2          RESULT
-----------            ----------            ----------        ----------
Webhook POST   ----->  AI: extract   ----->  Sheets: append    Row logged
(intake form)          JSON from note        (case-mgmt board) in board

if urgent:
FILTER                 ACTION 3
----------             ----------
is_urgent=true  ---->  Slack: notify
                       on-call mgr

Every node in the chain either transforms data (AI step, formatter) or sends it somewhere (Sheets, Slack, email). The skill is picking the right transformation at each node and passing data forward -- each action can use fields from every previous step. That last part is what makes the field-picker useful and what makes it feel like programming in slow motion if you are used to just writing result.field.

Lecture Notes -- Zapier Vocabulary
TermWhat it meansAnalog in code
Zapa complete automation -- trigger plus one or more actionsa running process or cron job
Triggerthe event that starts the Zap; every Zap has exactly onethe event listener or HTTP handler
Actiona step the Zap takes after the trigger; you can chain manya function call in the handler body
Taskone successful action run; Zapier bills by tasks consumed per montha billable execution unit
Patha conditional branch -- "if this condition, run these actions; else run those"if / else or a match arm
Filtera step that stops the Zap entirely if a condition is not met; nothing downstream runsan early return / guard clause
Storagea simple key-value store inside Zapier; persists small state between Zap runsa KV store or a global variable

The vocabulary that matters most for today is Filter vs Path. A Filter is binary -- pass or stop. A Path is a branch -- left or right. I use a Filter to block spam before I write anything to Sheets, and I use a Path to split urgent from normal so urgent gets an immediate Slack ping and normal rolls into a digest. Both are guard logic, but Filter ends the run and Path continues it differently.

Lecture Notes -- The Tool Comparison Framework

Zapier is not the only automation platform, and one of the things Phase 3 is explicit about is that nobody pays you to be a "Zapier expert." They pay you to solve a problem, and the tool is how you solve it. The relevant question is not "which tool is best" but "which tool fits this client and this workflow." The comparison framework has four columns: tool, strength, trade-off, when to use it.

ToolStrengthTrade-offUse when
Zapier5,000+ app integrations, UI anyone can learn, huge template librarytasks add up fast on paid plans; complex logic gets awkwardthe client needs to maintain it; the integrations already exist; simplicity beats power
Make.comvisual builder is cleaner for complex flows; more steps per scenario at lower costsmaller app ecosystem than Zapier; steeper initial learning curvemoderately technical client; multi-step flows that would get expensive in Zapier
Pipedreamcode-first (Node, Python, Go); full npm access in each step; generous free tierclient needs to read and edit code to maintain it; not a UI toolthe builder is technical; needs custom logic or an API not in Zapier; tight budget
Custom Nodefull control, zero per-task fees, runs anywhereyou own the infrastructure, the uptime, and every bug; setup cost is realhigh-volume, complex requirements, or a client willing to pay for a maintained service

The meta-skill is the table itself, not the rows. Being able to name the trade-offs and point a client toward the right fit is the thing that gets you paid $900 instead of $90. Anyone can follow a Zapier tutorial. Fewer people can look at a client's constraints -- their technical comfort, their maintenance situation, their budget, their integrations -- and say "here is why this is the right tool for you specifically." That is the conversation.

Lecture Notes -- Adding AI to a Workflow

AI steps in Zapier sit between a trigger and a downstream action and do one of four things: classify, extract, summarize, or generate. Those are not categories I invented -- the course is explicit about them, and they map to almost every real use case I can think of.

ModeWhat you give itWhat you get backExample in First 90
Classifya piece of text + a set of labelsone label from the seturgency = urgent / normal / spam
Extractmessy free text + a schemastructured fields (JSON)name, type, nextDate, urgency out of an intake note
Summarizea long document or threada shorter versiona weekly digest of who has what coming up
Generatea template + input variablesdrafted texta personalized reminder SMS for a resident

For this workflow, Extract is the load-bearing step. The intake note is unstructured -- a case manager or a resident types something like "D. has a parole check-in Thursday 9am and forklift cert class Mondays" -- and I need a clean JSON record to append to Sheets. The AI turns human language into a row the spreadsheet can accept. Without it, I either require a structured form (friction for the client) or I parse the note by regex (wrong 30% of the time and fragile forever).

Zapier offers two AI options: AI by Zapier, which is their native action that calls a model (currently gpt-5-mini under the hood), and chaining an OpenAI step directly with your own API key. AI by Zapier is simpler to wire and does not require managing an API key in Zapier's credential store. Chaining OpenAI gives you model choice, system prompt control, and response format enforcement. For this client, AI by Zapier is the right call -- if she ever needs to tweak the prompt she can find it in the Zap editor, which she already knows how to open.

Verbal Mini-Demo -- Walk The Zap, Name The Buyer

Two minutes to my partner, walking the First 90 workflow from trigger to result and naming who would pay for it.

Trigger: a Webhooks Catch Hook. When a resident's intake note hits the nonprofit's intake form, the form POSTs to a URL I own. Zapier is listening on that URL.

Action 1 -- AI Extract: gpt-5-mini receives the free-text note and returns a JSON object -- name, appointment type (job / court / parole / cert / housing), the next date, urgency, and a boolean isReal that tells me whether this is a real intake or noise.

Filter: if isReal is false, or if the type is not in the allowed set, the Zap stops here. Nothing gets written to Sheets, nothing pings anyone. The garbage stays outside.

Action 2 -- Google Sheets append: a new row lands on the case-management board -- resident first name, appointment type, date, urgency. Renee and her colleague can see it the moment it writes.

Paths: if urgency is urgent or type is court, an immediate Slack message goes to the on-call case manager's phone. Normal appointments roll into a Monday morning digest email so nothing drowns in pings.

Result: Renee's nightly hand-texting stops. A missed parole date becomes much harder, because the board sees it and the phone gets it.

Who pays: a small reentry or transitional-housing nonprofit. The director -- the person who hired Renee, who gets called when something falls through -- is the buyer. She is not paying for the automation. She is paying to reduce the probability that a missed parole check-in ends someone's housing, because that outcome costs her the grant. The hours are secondary; the stakes are the sale.

Partner's question: "What happens if the AI returns garbage -- like it can't find a date and just makes one up?"

My answer: Right now, not enough. The Filter blocks obvious junk by checking isReal and the type field, but if the model hallucinates a date that looks plausible, it writes to Sheets without complaint. That is a real hole, and it is exactly what Day 3 covers -- error handling, validation, and what to do when the AI step produces output that passes the filter but is wrong. For now the case manager still glances at the board each morning, which means there is a human in the loop catching the bad rows. Removing that human-in-the-loop review is Day 3's job, not today's.

The Thing That Clicked Today

I spent most of today wanting to write actual code. Every time I dragged a field into Zapier's mapping panel I was mentally writing the same thing as a destructuring assignment, and it was taking four clicks to do what one line does. That is a real fact about the tool and I am not pretending it is not. But somewhere in the middle of Exercise 5 -- when I rebuilt the same three steps in Pipedream and felt genuine relief at typing in a code editor -- the real question finally sharpened: who is maintaining this thing in six months?

Not me. Renee is. She knows how to open a Zap and click into a step and read what it says in plain English. She does not know what a destructuring assignment is and she should not have to. If I build this in Pipedream because it feels better for me, I hand her a system she cannot touch without calling me first, and calling me first means she will not call at all, and the system rots. If I build it in Zapier, she can tweak the prompt herself, add a new appointment type herself, look at the step that broke and understand what it was trying to do.

The thing that clicked is what "delivering" actually means. It does not mean handing over a thing that works. It means handing over a thing that keeps working after I leave -- which requires the person who stays to be able to keep it. I chose the tool that is worse for me and better for her. I think that might be the whole job.
