Sign Up + First Zap

Exercise 1 / 5 . Level 1-3 . 30 min

The point of this exercise is not to build something useful. It is to understand the loop: trigger fires, Zapier wakes up, action runs, result appears. Everything else -- the AI step, the webhook, the multi-step chain -- is just more nodes in that same loop. If I can wire one trigger to one action and watch data flow through the field mapping, I understand the fundamental thing. The rest is configuration.

Step 1 -- Account and first look

Zapier sign-up is unremarkable. The thing I made a deliberate choice about was the email trigger: the course suggests connecting Gmail, but I used Email by Zapier instead -- their robot inbox. Zapier assigns you a dedicated address like catch-hook@robot.zapier.com and you send test emails to it. No OAuth prompt, no "allow Zapier to read your entire inbox," no worrying about what permission scope I just granted.

As a coder, giving a third-party service broad read access to my actual email to run a tutorial exercise is a non-starter. The robot inbox sidesteps it cleanly. The educational value is identical and I keep my Gmail credentials to myself. I flagged this to the class because I think it is the right default for anyone privacy-conscious, not just me specifically.

Step 2 -- Wire the trigger

Trigger configuration for a new Email by Zapier event:

App:     Email by Zapier
Event:   New Inbound Email
Address: [Zapier-assigned robot address]

Fields available after trigger fires:
  {{ trigger.from }}       -- sender address
  {{ trigger.subject }}    -- subject line
  {{ trigger.body_plain }} -- plain-text body
  {{ trigger.date }}       -- timestamp

I sent a test email to the robot address. Zapier's test step showed me the raw data it received. This is the first thing that is genuinely useful about the UI: you can see exactly what the trigger produced, field by field, before you configure any action. When I write an HTTP handler in code I have to add a log line and redeploy to see the request. Here it is just there, labeled.

Step 3 -- Wire the action

Action configuration for Slack:

App:      Slack
Event:    Send Channel Message
Channel:  #intake-log
Message:  New intake received from {{ trigger.from }}
          Subject: {{ trigger.subject }}
          Body: {{ trigger.body_plain }}

The field-picker is how you insert {{ trigger.subject }} -- you click a purple "+" icon and browse a tree of available fields from every previous step. For two fields this is fine. My honest reaction is that it is slower than typing, and I keep having the impulse to just type the variable name directly. You cannot. The tool wants you to use the picker. The reason, I think, is that it validates that the field actually exists in the trigger data, which is a real guard against typos. I grudgingly accept this as a reasonable trade.

What this Zap is

An email routing rule with a destination that can be swapped out without touching email settings. I have always had email filters -- every mail client has had rules since the 90s. What Zapier adds is the action layer: instead of "move to folder," the action can be "create a Sheets row" or "run an AI step." This Zap is not impressive, but recognizing it as an email rule taken to its logical extreme meant I understood what I was building instead of just following steps.

Step 4 -- Add a Filter (Level 3)

Level 3 adds a Filter between the trigger and the Slack action. The requirement: only continue if the email subject contains the text "INTAKE." Any other subject stops the Zap cold -- no action fires, no task is consumed, nothing reaches Slack. 

Filter configuration:
  Field:     {{ trigger.subject }}
  Condition: (Text) Contains
  Value:     INTAKE

Result: Zap continues only if subject has "INTAKE" in it.
        All other emails stop here.

I tested this with two emails: one with subject "INTAKE: D. -- parole Thursday" (passes) and one with subject "Question about bus passes" (stops). Zapier's Zap History shows both runs -- one green with a check, one orange with "Zap halted by filter." The orange one is the useful one to see. The filter works and it costs nothing to run, because a halted Zap does not consume a task.

Filter vs. the alternative

The alternative to a filter is putting the condition in the action's logic, which means the action runs, realizes it does not need to do anything, and exits. You have paid for a task and done nothing useful. A filter is a guard clause at the architecture level instead of the function level, and the billing behavior is the concrete reason to use it early rather than late in the chain.

Deliverable

A live Zap: Email by Zapier trigger (robot inbox), Filter on subject contains "INTAKE," Slack action posting to a channel with the sender, subject, and body mapped from trigger fields. Two test runs documented in Zap History -- one that passes the filter and posts to Slack, one that is correctly halted. The loop is understood: trigger fires, data flows, filter guards, action runs. Everything from here is nodes in this same loop.
